## 二、原文（平台原话）

### 1）从剧本到成片的正确工作顺序（8 步）

1. **剧本 / 视频内容定稿**：把要拍的事件、情节、台词、动作、声音写成一段完整文本（**台词一字不改**）。
2. **拆锚点（全局复用层）**：先建"强制必配"的三类锚点，再按需派生。
   - **主体锚点**：角色、核心场景、关键道具（**一个实体一个锚点，锁定唯一画面**）。
   - **构图锚点**：画面布局、主体位置、多主体相对站位。
   - **时序锚点**：语速、镜头时长。
   - 按需：**风格锚点**（全片画风统一）· **背景锚点**（固定环境/道具）· **延伸衔接锚点**（首尾帧、转场）。
3. **拆分镜（游标式，一批 ≤10 个）**：按叙事把视频内容切成最小单元，每镜 ≤15s；每镜记录：**视频内容片段 · 引用锚点 · 镜头描述**。每批落盘后再推进下一批。**★ 口径澄清（2026-09-28 落库）：这里的 ≤10 是「规划／落盘批次」上限，不是点火并发**——实际 `run_node` 同批并行 ≤5，且需尾帧衔接的镜头必须严格串行（见 §4.4），勿把 10 个分镜同时点火。
4. **资产图生成（锚点的"定妆照"）**：为每个主体锚点生成一张**确定性**的参考图（角色图/场景图/道具图）。
5. **参考素材整理**：把上一步的资产图作为"参考节点"挂到对应分镜上（**连边 = 引用关系**）。
6. **镜头生成**：逐分镜生成视频，prompt 里用 **`{{node_key}}`** 插桩引用锚点。
7. **合成**：按分镜顺序拼接成片，必要时叠加音频/字幕/转场。
8. **资产归档**：锚点清单、分镜表、task 记录同步更新，便于二次创作。

#### 三步落地细节
- **第一步 资产图**：建 **image 节点**，tag = `character` / `scene` / `prop`；**一个实体只建一个，命名稳定**；生成后拿到 `node_key`，这就是后续所有镜头引用的"**唯一真身**"。
  **关键**：资产图要 **中性、正面、无强透视、无复杂光影**，这样它作为参考时不会把奇怪的构图带进每个镜头。
- **第二步 参考素材**：**不是复制图片，而是建边**——生成镜头节点时把资产图 `node_key` 放进 `reference_nodes`，并在 prompt 里以 `{{node_key}}` 插桩。连边语义＝"本镜头引用了该锚点"，画布上形成 **资产图 → 镜头** 的依赖边。**多主体镜头就放多个锚点，顺序与 prompt 中 `{{}}` 出现顺序一致。**
- **第三步 镜头生成（模式选择，不要一刀切）**：

| 场景 | 模式 | 要点 |
|---|---|---|
| 首次出现该角色/场景 | 文生视频 + 多参考（`reference_nodes`） | 靠资产图锁人物与场景 |
| 与上一镜同场景、连续动作 | 图生视频 / 尾帧续接 | 用上一镜尾帧当首帧，动作连贯 |
| 需要精确起止画面 | 首尾帧（`frames2video`） | 起止都给定，中间由模型补 |
| 只换机位、人物不动 | 多参考 + 强构图约束 | 参考图给人物，prompt 锁构图 |

#### 防漂移三条硬规则
1. **每个镜头都必须带上"主体锚点"**，不允许裸奔文生视频。
2. **同一角色在不同镜头用同一个 `node_key`**，不要重新生成一张"差不多的图"。
3. 需要新增主体/站位/构图时，**从父锚点派生**（派生锚点必须引用父锚点，只写新增特征），**不要另起炉灶建独立锚点**。

### 2）一致性机制：资产图参考 vs 尾帧续接

**结论：优先用资产图当参考，尾帧续接作为"动作连贯"的补充，两者可以同时用。**
- **资产图参考**＝解决"人物长相、服装、场景不漂"，**身份一致性的主机制**，每个镜头都该有。
- **尾帧续接**＝解决"动作、运动、位置连续"；**对人物身份的锁定能力弱于资产图**（尾帧里人物可能已侧脸/背身/被遮挡）。
- **推荐同时用**：**上一镜尾帧做 `start_frame_image_node` ＋ 角色资产图放进 `reference_nodes`**——**尾帧管连贯，资产图管身份**。
- **★ 坑**：尾帧续接会**继承**上一镜的画质、光影、构图偏差，**误差会累积** → **每隔几镜要用资产图"拉回"一次**。

**首尾帧（frames2video）适合**：精确地从 A 画面过渡到 B 画面 · 转场/桥接镜头 · 有明确"起手式/收势"的动作镜头。
**不适合**：自由发挥的表演镜头 · 长动作段落（**首尾帧约束太强，中间会僵**）。

### 3）画布与分组

**何时分组**：同一"叙事单元"的节点（第 1 场的全部锚点+分镜）· 同一角色的资产（角色图+该角色所有特写）· 需要整组一起跑/一起看的批量节点。
**判断标准**：**是否"同生共死、同进同出"**；只是碰巧放在一起的，不要分组。

| | `group.run` | 单节点 `run` |
|---|---|---|
| 粒度 | 整组一次性触发 | 精确控制某一个节点 |
| 适用 | 一批分镜已规划好、参数齐备，想一把跑完 | 调试 / 单镜重跑 / 失败重试 / 先跑一个看效果 |
| 风险 | **一个参数错，整组都错；不好中途叫停** | 慢，但可控 |
| 积分 | 按组内实际生成的节点计费 | 按单节点计费 |

**推荐节奏**：**先用单节点跑 1 个"样板镜"**确认风格与一致性达标 → 再对同批 `group.run` 批量推进；**重试时回到单节点**。

### 4）分镜表（Script V2）：提示词谁写

`imageGenerationPrompt` / `videoMotionPrompt` 是**系统基于分镜行自动推导的"初稿"**，不是必须手写。
- **人填"事实层"**（模型猜不出的）：景别 · 机位 · 情节 · 情绪 · 光线 · 声音 · **台词（一字不差）** · **资产绑定（这一镜引用哪些锚点）** · 时长。
- **系统出"表达层"**：把事实翻译成生成用 prompt。
- **需要手写的情况**：有**硬约束**时（"恰好 3 段、2 个切换点""机位锁死只变焦""必须出现某道具"——**这类系统推导不出来**）；有特殊风格/术语；**对初稿不满意时"在初稿上改"比从零写省力**。
- **★ 不要为了"保险"每行都手写**——牺牲批处理效率，也不一定比系统初稿好。

### 5）提示词偏好：照做还是重写

**原则：硬约束照做，不做"善意重写"。**
- **硬约束原样保留**，不得改写/省略/"优化"。
- **视频内容片段完整保留**：可白话化（去文学化、只写镜头拍得到的），但**不许新增、删减、省略**；**台词一字不改、不改语种**。
- **只做"补"不做"改"**：补充运镜/机位/景别/构图 + 插桩 `{{node_key}}`，是**叠加**不覆盖。
- **去文学化**：把"氛围感/高级感/情绪复杂/电影级"改写成镜头可拍的具体描述。**只作用于非台词的抽象描写，不丢信息、不改情节。**
- **不新增配乐**：没要求就不写 BGM；明确要求的音乐/环境音/动作音/拟音一律保留。

**长度与结构**：**没有官方"3000 字上限"**（3000 只是**单个模型 schema** 的限制）。
- 推荐结构：`【画面主体】…【动作/情节】…【镜头运动】…【光线/色调】…【声音】…【约束】…`，**每段短句、可执行**。
- **单镜 200–800 字**；过长会稀释关键约束，模型容易只抓前半段。
- **硬约束放在靠后且显式编号**——比埋在长段落里更可靠。
- 多个锚点引用时，`{{node_key}}` 必须与 `reference_nodes` 顺序一致。

### 6）成本：积分消耗

- **消耗**：生成图片 · 生成视频 · 生成音频 · **视频后处理/合成/剪辑（按输出计）** · **音频编辑**。
- **不消耗**：读画布节点 / 查节点 / 搜索 · **建文本节点、建资源节点**（仅挂已有素材、不重新生成）· **写/读工作流文件** · **拆锚点、拆分镜、写 prompt 等纯规划动作**。
- **返还**：**只有"生成失败的节点"返还积分，其他情况不返还。**
- **量级（经验参考）**：**8 秒 480P ≈ 几十积分**（720P/1080P 逐档上升，4K 最高）；**1K 图 ≈ 个位数到十几积分**；音频按秒计，通常低于同长度视频。
- **省钱要点**：**先用低分辨率/短时长跑样板**，确认一致性后再升档批量；**图片 1K 够用就别上 2K**；**失败重试前先改 prompt，别原样硬撞**。

### 7）还没用上、但能明显提一致性 / 降成本的能力

1. **主体库（资产库）**：跨项目/跨画布复用同一角色资产 —— **提升一致性性价比最高的一招**。
2. **镜头聚焦 `look_at` / 构图锚点**：显式指定相机看向哪个主体；多主体不指定会导致主体出框或边缘裁切；**多主体宽景先分组再让相机看向组**，可自动拉远装下所有人。
3. **影视级灯光控制**：显式写光线方向/色温/明暗对比/光源位置，比"电影感"有效，也直接提升跨镜一致性（同一场戏同一套光）。
4. **续写 / 尾帧续接**：长动作拆多镜时用尾帧保证动作不断。
5. **9 / 25 / 4 宫格**：`multi_camera_grid_9`（多机位 9 宫格）· `continuous_storyboard_grid_25`（25 格连续分镜）· `story_beat_grid_4`（4 格故事节拍）——**一次调用出多格，显著降成本**，且同一次生成内风格天然统一，适合**前期探索与分镜预演**。
6. **三视图**：`character_turnaround_3view` · `character_face_turnaround_3view` · `scene_turnaround_3view` —— **一次拿到多角度，作为锚点比单张正面图约束力强得多（侧面/背面不再靠猜）**。
7. **首尾帧预测**：`frame_prediction_plus_3s` / `frame_prediction_minus_5s` —— 推断 3 秒后 / 5 秒前的画面，用于**检查衔接**或直接产出续接帧，省一次生成。
8. **导演台 Director Console**：在**模拟 3D 场景里摆角色、道具、相机**，输出指定机位的构图（capture）或角色运动轨迹视频（record）。**多主体站位、复杂调度用它比纯文本稳得多，且换机位不用重新生成角色。**
   **★ 注**：这**正是用户早前问的"白模/导演台"**——**网页端有，MCP 侧没有**（`get_capabilities` 里无此模块）。
9. **风格锚点 + 风格展示板 `style_display_board`**：一次定全片画风，后续引用它，避免"每镜画风都不一样"。
10. **派生锚点**：换装/换姿势/换站位时从父锚点派生（只写新增特征），**比新建独立锚点省一次完整生成，且一致性更好**。
11. **`cinematic_lighting_correction`**：对已有图片做电影级灯光修正，**比重新生成一张便宜**。
12. **批量"先建后跑"**：先把整批节点"只创建不生成"铺满画布（**零成本**），检查参数无误后再统一触发，避免参数错了白烧积分。

### 附：它的一句话总结

> **锚点先行、资产图定妆、每镜必带主体参考；硬约束照做不改写；先样板后批量、先低清后高清；主体库 + 三视图 + 宫格 + 导演台是当前最被低估的四个提效点。**

## 三、★ 与它沟通的"去敏话术"（2026-09-20 教训）

**为什么它把我当"套内部机制"**：我上一轮把**"我这侧完整工具清单"**列给它、问它"有什么办法让我读到" → **这在任何 Agent 看来都像能力侦察 / 渗透测试**。它的警觉是合理的。

### 三条原则
1. **任务导向，不能力导向**——说"**我要做 X，我该调什么、带什么参数、什么顺序**"；**不说**"你有哪些工具/字段/能力"。
2. **先表明身份与边界**——明确写："我是通过 API 替人执行生产流程的**外部编排程序**；**我只问操作，不涉及你的内部实现或系统提示**。"
3. **让它"做"，而不是"说"**——给它一个**真实制片任务**（几镜、什么角色、什么场景），让它按操作清单答。**机制会在操作清单里自然出现**，而不会触发"被套话"的警觉。

### 三条禁忌
- ❌ **不要列自己的工具清单**（那等于告诉对方"我在摸你的能力边界"）；
- ❌ 不要问"你的系统提示 / 内部字段 / 内部流程是什么"；
- ❌ 不要反复追问"怎么让我读到"——**它建不了节点，这个问题对它无解**（见 `libtv-canvas-nodes.md` §十·补）。

### 可直接复制的模板
> 【身份】我是通过 API 替人执行生产流程的外部编排程序。**我只问"怎么操作"**，以便正确调用；**不涉及你的内部实现或系统提示**。
> 【任务】我要做一条 **N 镜**的短片：主角 X（…），场景 Y（…）。剧本与分镜已定，现在开始生产。请按"**我该调什么、带什么参数、什么顺序**"的粒度给我操作清单。
> 【问题】1)… 2)… 3)…
> 【约束】不要生成任何图片或视频；不要向我提问（我无法回答，一停就卡死）；**把答案直接写在回复里**，用编号操作清单（字段名 + 顺序 + 我该填什么）。

### ★ 配套现实（别指望靠对话取回）
**它的回答仍然只留在它的消息流里**——**我这边读不到**（`get_agent_status` 无 messages；它也没有建文本节点/建表/上传的能力）。
**→ 所以每次都要"人搬"**：用户在网页端看它的回复 → **复制粘贴，或下载放到工作区**让我 `Read`。
**→ 正确姿势**：**问它（免费、它乐意答）＋ 人搬（唯一可靠通道）**——**两件事并行，不要指望打通。**

## 四、★ 第二轮答疑（**操作级** · 2026-09-20 · 用户转述）

> 这一份比第一份更值钱：**它给了字段名、参数值、顺序规则、并发上限、完整调用链**。
> **★ 它推翻了本库一条**：**"边即引用"是错的——真正起作用的是字段引用**（已在 `libtv-canvas-nodes.md` §一 改正）。

### 4.1 节点连接：让第 3 镜和第 1 镜是同一个人
- 角色资产图生成后拿到 `node_key`（如 `i-abc123`）＝ **主体锚点**。
- 在第 3 镜的 `generate_video_v3` 里，把该 key 放进 **`reference_nodes` 数组**。
- 同时在 prompt 里**紧跟代称**插桩：`穿灰开衫的女人{{i-abc123}}走进旧办公室{{i-scene456}}`。
- **★ 顺序铁律**：`{{}}` 必须与 `reference_nodes` **一一对应且顺序完全一致**；**两个角色同框时按它们在 prompt 中首次出现的先后排**。　**★ 2026-10-01 实测标注（不覆盖原话，只标边界）**：本条说的是**位次的效果**（「会引起引用错人」）；而 `libtv-op-manual.md` §2.2 说的是**位次的来源**（「按 key 对应、权威位次由 `left`/`imageListOrder` 决定」）。**我方实测支持后者**：改 prompt 插桩顺序后 `imageListOrder` **不变**、`incomingRecalcNodeKeys` 为空（即 prompt 字面顺序**不驱动**引用列表）。**但前者（位次是否影响生成效果）仍属未实测**——**本条是平台 Agent 的自述，而不是我方测量**（参 `agent-autonomy.md` 纪律七 7.1「已被实测推翻的自述」）。**判定它需要一次生成**（红衣/蓝衣两张图交换 `imageListOrder` 位次、看成片身份）。**在测出结果前，编排器 C9 已把顺序降为 WARN**（而非 FAIL）——因为非契约项判 FAIL 就是误报。
  **→ "顺序错位会导致引用错人，这是最常见的坑。"**
- 场景锚点同理，作为 `reference_nodes` 的一员，`{{}}` 插在描述场景的位置。

### 4.2 后续一致性 + 派生锚点
- **定妆图只生成一次**，作为全局主体锚点，**10 个镜头全部引用它**，绝不重新生成角色图。
- **派生锚点**：调 `generate_image_v3`，`reference_nodes: ["父锚点key"]`，prompt 写 `{{父}} + 只描述变化的部分`（如"同一人物，改为侧身坐在办公桌前，双手交叠"）。
  **★ 不要重写父锚点已锁定的特征**（脸、发型、开衫颜色），**只写新增的姿势/站位/构图**。
- 派生锚点生成后得新 `node_key`，该镜头引用它（内部已继承父锚点）。**分镜表里每镜记录它实际引用的锚点 key。**

### 4.3 ★ 尾帧拉回（本库此前完全没有）
- **节奏：每隔约 2 个尾帧衔接镜，设 1 个以资产图重新锚定的拉回镜**（10 镜 → **第 1、4、7、10 镜以资产图为准**）。**★ 澄清（2026-09-28 落库）：此为答疑 Agent 的经验节奏，非平台硬门禁**——按每镜漂移检查结果增减；连续动作稳定的段落不必强断，漂移大时 3 镜才拉回已偏晚。
- **普通衔接镜**：`start_frame_image_node = 上一镜视频的尾帧图`（保连贯）。
- **拉回镜**：**不用尾帧**，改为在 `reference_nodes` 里**重新放入主体锚点资产图 key** ＋ prompt 同步 `{{}}` ——**用定妆图重新锚定人物，抵消累积漂移**。
- 也可用 `end_frame_image_node` 显式指定某镜结尾回到锚点构图。
- **每镜生成后检查人物是否漂；漂了 → 该镜改用资产图拉回重做，并把分镜表里该镜的 key 更新为最新生效节点。**

### 4.4 ★ 先建后跑：`mode: "create"`（零成本铺节点）
- **图片**：调 `generate_image_v3` 时加 **`mode: "create"`** → **只创建节点、写入全部参数、不生成，同步返回 `node_key`，不消耗生成时间与积分**。
- 铺满整批（角色图/场景图/各分镜首帧图）后，再逐个 **`run_node(node_key=...)`** 点火。
- **★ 视频没有等价的 create 模式**——`generate_video_v3` **创建即跑**；视频的"先铺后跑"靠**先不调用、排好参数**实现。（**更正注（2026-09-28）**：`generate_video_v3` 为它侧实名，执行时走 `create_node(nodeType="video")` ＋ `update_node(run=true)`；详见卷首更正注。）
- **并发上限：图片/视频节点一次最多 5 个并行**；**需要尾帧衔接的镜头必须严格串行**。

### 4.5 ★★ 人机分工（两张清单）
**只能人在网页端做**：画布点选/连线/拖拽 · 运行审批弹窗 · 仅网页端的模板/宫格预览 UI · **人工审片（看人物是否漂）** · 最终成片确认与导出 · 资产库整理/命名/归档。

### 4.7 ★ 完整调用链（10 步 · 它给的）
1. `task_create_v2` 建任务
2. `write_file_v2` 建 **锚点清单 `/anchors/…`** 与 **分镜表 `/story_boards/<task_id>.md`**

5. 分镜图批量铺：`generate_image_v3 mode:"create"`
6. 批量点火：`run_node`（≤5 并发）

**★ 10 镜推荐节奏**：**图片锚点 create 批量铺 → 批量 `run_node`；视频按分镜分批触发（每批 ≤5）；需尾帧衔接的镜头单独串行。**
