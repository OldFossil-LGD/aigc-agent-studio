## 一、★★ 点火链（R33 · 最重的一条纪律）

> **唯一一条"自动化里绝对不该直接调"的接口级依据**：**不应绕过审批、直接对节点调用点火**。

**理由（它给的接口级依据）**：点火**真实提交生成、扣费**，**默认非幂等**，且**点火后没有取消接口**；契约要求**批量真实运行前必须经 `ask_human(mode=approve_run_node_once)` 审批**，**授权仅对当批列出的 `node_key` 生效**。
**→ 结论：`create_*_node` 只写参数不扣费，可以安全自动化；唯独"点火"这一步不得在无人审批下被自动调用。**
**★ 这条直接支持本库的"阶段门"纪律，且给了接口级依据。**

### 1.1 职责边界（它给的拆分）
| 原语 | 语义 | 是否扣费 |
|---|---|---|
| **`update_*_node`**（不带 run） | **只改参数**；节点改完回到"**已创建**"态 | **不扣费、不运行** |
| **`run_node`**（它侧点火原语） | **对已写好参数的节点提交一次运行** | **扣费** |
| **`[]` 显式提交**（它称 `submit_generation`） | 针对**参数已落定**的节点提交生成任务，**不负责改业务参数** | 扣费 |

**★ 关键**：**"没有 `update 同时 run` 的开关"**（它这么说的）→ **但我侧 `update_node` 的 schema 里确实有 `run` 字段**；**点火时跑的是"节点上已存的参数"，`run_node` 不重传业务参数**（它明确：`run_node` 必填 `node_key`，可选 `title`，**运行以"画布当前节点"为准**）✓
**→ 正确顺序：先 `update`（改参，节点回到"已创建"）→ 再点火一次。** **绝不"既改又交叠提交"**（两次独立提交＝两个任务＝重复扣费/重复产物）。

### 1.2 重跑 = **有意的"作废并重做"，不是无害重试**
- 一旦重新点火，**节点上"当前任务"指向新一次运行**；**旧 `taskInfo` 作为历史保留可追溯**；**结果回到同一 `node_key`（不新建节点），但是一次新生成**；
- **覆盖前没有内建二次确认，也没有自动幂等键** → **确认只能来自流程层**（审批）；
- **受其影响的下游节点结果应一并视为作废**。

### 1.3 返回结构怎么读
- **任务句柄**：`task_id` / `generation_id` / `job_id`（**单次运行句柄**）；**`node_key` 是稳定节点句柄**（产物最终回放到 `node_key`）；
- **"是否真的提交"**：布尔字段 `submitted` / `accepted` / `enqueued`；
- **★ `accepted=true` 只代表"已入队"，不等于"生成成功"**——最终成败要看任务/节点状态。

### 1.4 幂等
- **点火（`run_node` 类）默认非幂等**：每次有效触发＝一次新生成、重新扣费；**契约未暴露幂等键入参** → **重试防重必须由编排层自己保证**（节点已在 `generating` 就拒绝重复 run）；
- **显式提交类**在**提供幂等键**时具备幂等（同键同目标 → 返回首次任务）；
- **幂等键字段名**：`Idempotency-Key`（HTTP 头层）或请求体里的 `idempotency_key` / `request_id`；**放在传输/请求控制层，不要混进 prompt**；
- **TTL 未公布**（通用实践分钟级~24h）→ **不要假设跨天仍去重**；安全做法＝**同一逻辑提交用同一键、新意图换新键**。

### 1.5 ★ 回滚：**没有取消接口**
- **工具集中没有 `cancel_generation` / kill job，也没有"参数回滚到上一版"的自动撤销** → **提交后通常只能等它完成或失败**；
- **正确的"回滚"是账本层面的处置**：① 参数错 → 等结束 → `update` 修正 → 重新 run ② **失败节点不要在原 node 上无脑重跑** → **标"已废弃" + 新建节点（标题加 v2/v3）+ 留痕失败原因** ③ **引用变化会沿引用链作废下游**；
- **→ 自动化里应"先审批/先校验再点火"，因为点火后没有便宜的撤销键。**

## 二、★ 审核三阶段（R33 · 极清晰的一张判据表）

| 阶段 | 典型码（**它声明是通用风格、非平台逐字**） | 文案样例 | **拦截点** |
|---|---|---|---|
| **① 提交前**（参数/计划校验） | `INVALID_ARGUMENT` / `PARAM_OUT_OF_RANGE` | "duration_sec out of supported range: model Seedance 2.0 accepts 4–15 seconds"；"model/type mismatch: audio type does not match ai_model" | **入队之前，任务根本没创建（`accepted=false`）；不扣费或计费前拒绝** |
| **② 生成中**（安全策略命中） | `CONTENT_POLICY_VIOLATION` / `MODERATION_BLOCKED` | "Your request was blocked by content safety policy. Please revise the prompt and resubmit." | **已提交、在生成流水线中被拦，任务终止而非产出** |
| **③ 产物审核**（生成后复检） | `OUTPUT_REJECTED` / `POST_GENERATION_REVIEW_FAILED` | "The generated output failed safety review and cannot be displayed." | **已产出但成品未过审 → 节点无可用产物或产物被屏蔽** |

**★ 区分要点（一句话）**：**提交前拒绝＝没有任务 · 生成中拦截＝有任务但被终止 · 产物审核＝跑过了但结果不可用。**

**★ 审核拒绝 vs 生成失败的三个判据**：
1. **看 `error_code` 所属域**——`MODERATION`/`CONTENT_POLICY`/`OUTPUT_REJECTED`＝**审核域**；`INFRA`/`TIMEOUT`/`RESOURCE`/模型内部错误＝**技术域**；
2. **看 `review_stage`**（`INPUT` 拦输入 / `OUTPUT` 拦产物）——**技术失败一般没有 `review_stage`**；
3. **看可重试性**——技术失败常 `retryable=true`（同参数可重试）；**审核拒绝 `retryable=false`，必须改 prompt，原样重跑仍会被拒**。
**→ 节点处置**：审核拒绝/失败的节点应**标"已废弃"**，**改内容后新建 v2**，**不在原节点反复撞审核**。

**★ 它说"没有独立 `validate_generation_plan`/dry-run 自检接口"** → **但我方 MCP 侧实测有**（schema 已拿到）→ **再次属工具面混淆**；不过它列的"**内建前置校验**"有效：**时长域校验 · 模型/类型匹配 · 引用完整性（`node_key` 必须存在且已生效，且必须在 prompt 中以双花括号插桩；未生效不运行）· 状态校验（`generating` 时 run 直接失败）**。

## 三、★★ 导演台 `director_apply`（R29 · 完整答案）

### 3.1 可直接从 MCP 调用
**它是一等工具，不必借 `run_agent` 的 skills 通道**。**最小入参：`{commands: [<一条命令>]}`**（只需 1 条原子命令即可成立）。

### 3.2 `commands` 的 14 个 op（**必填/可选**）
| op | 必填 | 关键可选 |
|---|---|---|
| `add_character` | `op` · `ref` | `body` · `at{x,z}` · `facing` · `color` · **`from_ref`**（引用图片节点重建姿态） |
| `add_prop` | `op` · `ref` · **`asset`** | `at{x,z}` · `rotation_deg` · `scale` · `color` · **`image_ref`** |
| `add_camera` | `op` · `ref` | `shot_size` · `angle` · `facing` · `side` · **`look_at`** · `fov` · `at{x,z}` |
| `add_empty_object` | `op` · `ref` | `at{x,z}` |
| `add_group` | `op` · `ref` · **`members`（≥2）** | — |
| `update` | `op` · `ref` | 按实体类型给（`at`/`rotation_deg`/`scale`/`color`/`shot_size`/`angle`/`look_at`/`fov`/`facing`/`pose`/`asset`/`image_ref`） |
| `remove` | `op` · `ref` | — |
| `set_environment` | `op` | `sky_color` · `panorama_ref` |
| `set_duration` | `op` · **`seconds`** | — |
| `animate_character` | `op` · `ref` · **`keyframes`**（每项 ≥ `at_sec` + `at`/`facing`/`pose` 之一） | `walk_cycle` · **`path`** |
| `animate_camera` | `op` · `ref` · **`moves`**（每项必填 `from_sec`/`to_sec`/`preset`） | `keyframes` |
| **`capture`** | `op` | `ref` · **`views`（current/4/12）** · `aspect_ratio` |
| **`record`** | `op` | `aspect_ratio` · `resolution(720p/1080p)` · **`continue_from`** |
| `read` | `op`（单独只读，无需 `base_revision`） | — |

### 3.3 `base_revision` / `target_node`（**关键区分**）
- **`base_revision`**：来自**上次 `director_apply` 返回结果里的 `revision` 字段**（`r_` 前缀哈希）——**它是"场景修订哈希"，不是 `node_key`**；
- **★ 不传会怎样**：**不报错、也不静默覆盖最新**；**不传 `base_revision` 且不传 `target_node` ＝ 起一个全新 Director Console（新场景），旧场景原样保留**；
- **要在同一场景续改 → 传 `target_node`**（操作路由到该节点）；`base_revision` 仅用于**同一布局上的增量 refine**；
- **`target_node` 只接受"导演台节点"（`n-` 前缀）**；**image / video / scene / group 一律不接受**（报错码未映射）。

### 3.4 ★★ 手绘轨迹：**能传什么、不能传什么**
| 要素 | 能否传 | 说明 |
|---|---|---|
| **贝塞尔控制点** | **❌ 不能** | **无贝塞尔/曲线控制点字段** |
| **关键帧序列** | **✅ 能** | `animate_camera.keyframes`（`at_sec` + `shot_size`/`angle`/`look_at`/`fov`）· `animate_character.keyframes`（`at_sec` + `at{x,z}`/`facing`/`pose`）；**对象数组、时间用秒、位置用归一化舞台坐标 x∈[-1,1] z∈[0,1]** |
| **路径点数组** | **⚠️ 部分能** | 角色可用 `path`（**只接受三种预设：`line`/`ring`/`rectangle`**）+ keyframes 的 `at` 点；相机用 `moves` 的 **7 个命名 preset**（`orbit`/`half_arc`/`push_in`/`pull_out`/`pedestal_up`/`truck_right`/`spiral_up`）；**没有任意自由路径点数组字段** |
| **幅度与时长** | **时长✅ / 幅度❌** | 时长能传（`moves.from_sec/to_sec`、`set_duration.seconds`、`keyframes.at_sec`）；**"幅度"无独立标量字段**，只能靠 preset 选型 + 起止 keyframe 的 `at`/`shot_size`/`fov` 差值**间接表达** |

**★ 结论**：**无法精确复现任意自由手绘曲线**（无贝塞尔、无自由点数组）→ **MCP 侧只能"关键帧 + 预设运镜"近似；要逐像素一致，必须回客户端手绘。**

### 3.5 机位参数（**没有独立的高度/距离字段**）
- **高度**：**无独立数值字段** → 通过 **`angle`** 间接表达（`level` / `bird_eye`=高机位 / `worm_eye`=低机位 / `over_shoulder`）；
- **焦段/取景**：**`shot_size`**（`closeup`/`close`/`medium`/`full`/`long`）+ **`fov`**（**20–90 度整数**）；
- **与主体距离**：**无独立距离数值** → 靠 `shot_size`（近—远）+ **相机 `at{x,z}`**（**z=0 最近、z=1 最远**）+ `look_at` 共同决定；
- 其他：`facing`（camera/away/left/right）· `side`（front/left/right/back）。

### 3.6 ★ 产物形态：**是真出产物，不只是参数**
- **`capture`** → **静态构图（构图锚点）**，可 `views=current/4/12` 多机位；**落到画布的图片节点**；
- **`record`** → **角色动作轨迹视频（运动锚点，真实可预览）**，可 `continue_from` 串联、可设 `aspect_ratio`/`resolution`；**落到画布的视频节点**；
- **未执行 `capture`/`record` 时，场景本身只是可 `read` 的布局参数**。

### 3.7 ★★ 两条要标注的差异
1. **改场景不会自动让下游失效**——**工具契约未声明 `director_apply` 会把下游已生成的图片/视频标记失效或过期**；**场景侧有 `revision`（`r_` 哈希）可判断"场景已变"，但它不自动传播为下游的过期标记**；**是否有显式下游过期状态字段：未映射**。
   **→ ⚠️ 与 R12 的"**被引用节点变更会级联作废**"口径不同** → **可能：节点级级联作废成立，但"导演台场景 revision 变化"不传播** → **按差异记，施工时以"手动管下游"为准**。
2. **`director_apply` 的计费规则：未映射**（按命令条数/按场景/免费均无记载）；**但 `capture`/`record` 会产出画布媒体节点** → **是否计费需以实际为准**。

### 3.8 ★ 适用边界（它给的一条）
> **仅当需求是"有明确空间站位、机位与运动轨迹、需要 3D 空间预演/走位与运镜可视化"时，用导演台替代手工场景描述；纯氛围、光影、风格、情绪类或无明确调度的场景，仍用自然语言场景描述，不进导演台。**

## 三·补 · ★★★ 导演台产物的**用法**与"什么时候该上"（R35 `i-yy3n6uxcs9aw`）

### 3补.1 ★★ `record` 的"运动锚点视频"怎么用（**唯一明确支持的喂法**）
- **它是一个普通 VIDEO 节点** → **可以放进视频生成节点的 `reference_nodes`**，并在 prompt 中以**双花括号 `node_key`** 插桩、**写明用途**："**以此灰模视频的相机运动轨迹/走位为运动参考，替换为写实角色与真实场景**"；
- **★ 当首帧/尾帧：不能直接放**——**`start_frame_image_node` / `end_frame_image_node` 只接受 IMAGE 节点 key** → **要把视频某一帧当首帧，必须先"取帧成图"**（编辑工具支持把首/尾帧提取为 image 节点），**再引用那张图**；
- **当续写源：可以，且这是导演台自带的正路**——**下一次 `director_apply` 的 `record` 用 `continue_from` 指向上一镜 `record` 的视频节点 key**；
- **（普通视频节点的续写是另一条路径：`video_action_type=extend` + `reference_nodes` 放被延长的视频）**

### 3补.2 ★ `capture` 的产物形态与用法
- **`views=4/12` 产出的是"多张各自独立的视点图"，不是一张拼图**；**拼图类多宫格是图像模型的 `prompt_template`（如 `multi_camera_grid_9`），与导演台 `capture` 不是一回事**；
- **画布落点（一个节点还是多个）契约未明确 → 以实际返回的 `node_key` 数量为准**；
- **`views=12` 的计费口径未映射 → 建议先用 `views=4` 试一次、以实际扣费确认，不要凭推测放开用**；
- **★ 可当"机位/构图/站位故事板"（blocking / staging board）**——空间关系、机位角度、透视、角色位置**几何精确**，多视点**严格来自同一场景、一致性强**。

### 3补.3 ★★ 三条硬限制（**必须知道**）
1. **`n-` 导演台节点不能直接写进视频节点的引用**——**下游引用的是它 `capture` 出的 IMAGE 节点或 `record` 出的 VIDEO 节点**；**`n-` 是控制台节点、`r_` 是场景 revision，二者都不是可喂给模型的媒体素材**；
2. **★ 场景 `revision` 变了不会自动级联失效**——**下游引用的是 `capture`/`record` 的产物节点，不是 `r_`**；**要人工排查**：用 **`search_canvas_nodes`（按 `node_type`/`name`/`tag`/`parent_keys`/`child_keys` 过滤）** + **`get_node_details`（读 `agent_task_params` 里的 `reference_nodes`/`start`/`end_frame`/`continue_from`）** 逐个筛；**`record` 链可顺 `continue_from` 追**；
3. **灰模不带服化道**——**`body` 预设（`mannequin`/`female`/…）只是占位体型/动画骨架，与最终角色的脸/发型/服装无关、也不会被继承**。

### 3补.4 ★★ 导演台 vs 图像模型故事板（**分工**）
| | **导演台 `capture`** | **图像模型故事板** |
|---|---|---|
| 强项 | **空间/透视/机位几何精确** · 同场景多视点**天然一致** · **可先验证调度再投入高成本生成** · 可反复 `record` 改轨迹 | **有氛围/光影/服化/表情/画风**，可直接当**美术与情绪参考**（还可用 `story_beat_grid_4` / `continuous_storyboard_grid_25` 出多格） |
| 弱项 | **灰模无表演/无光影氛围/无服化道细节**，是"**技术预览**"不是"美术故事板" · 多一道中转 · views 多计费不确定 | **空间几何与多镜一致性靠运气**，机位/透视**不精确** |
**→ 建议：要"调度与机位精确"用 `capture`；要"情绪与美术表达"用图像模型。**

### 3补.5 ★★ "正对中轴单点透视"在导演台里怎么精确表达
**能**：`add_camera` 用 **`angle=level`**（水平）· `shot_size` 按需 · **`look_at` 对准角色**（角色放 `at x=0`）· **相机本身也摆在 x=0 的中轴上** · **`fov` 固定一个值并在所有镜头保持不变**。
**★ 关键**：**`fov` 固定 ＋ 相机与角色 x 都为 0** 是核心；**仅写"角色 at x=0"不够，必须保证相机也在 x=0，否则会产生斜角**。
**★ 但**：**若全片不动，直接用一张正面锚点图当首帧、锁定 `fov` 与构图，比每次在导演台重建相机更省事且更可控。**

### 3补.6 ★★★ 判据：**什么时候该上导演台**（它给的唯一一条）
> **当"机位 / 走位 / 多角色调度的几何精确性"已经成为主要风险、且光靠首帧和锚点图压不住时，才上导演台；**
> **凡是一致性问题主要出在角色外观（脸/鞋/服）或镜头基本固定的，一律不上导演台，直接用角色锚点图 + 首帧锁定。**

**→ 换句话说**：
| 该上导演台 | **不该上** |
|---|---|
| **多角色 / 多站位** · **复杂走位** · **有明显运镜调度（推拉摇移/绕）** · **机位 ≥3、需保证各机位空间自洽** · **需要先验证相机路径再批量生成** | **单角色 + 固定机位**（如全片正对中轴）· **一致性问题主要在"脸/鞋/服"** · **纯氛围/光影/风格/情绪类场景** |
| **★ 它能帮的是"位"，不是"相"**（灰模只精确在站位/走位/相机轨迹） | **它的产出必须再交给图像/视频模型细化**，不是成片 |
