## 1 · 四层验收（A 路 `00_总纲` §6 的口径）与 C 路的责任边界

A 路把验收分四层。**C 路只负责其中两层**，另两层的归属写在括号里，**不许越级冒充**：

| 层（A 命名） | 判什么 | 判据来源 | 谁负责 | 能不能机判 |
|---|---|---|---|---|
| **structure** | 节点/边/分组/引用/位次/派生字段是否合法闭合 | `project_info.connectionList` · `read_node` · 本文 §3 | **C 路** | **能**（离线可复算） |
| **instruction** | 提示词是否表达了要求 | prompt gates · 对表 | **B 路** | 能（见 `13_提示词门禁与失败诊断.md`） |
| **technical media** | 媒体是否真的落盘、可解码、容器参数是否符合声明 | `read_node` 的 `url` · `inspect_media` · `export_readiness` · `ffmpeg -i` | **C 路** | **能**（但要回读真实产物） |
| **creative acceptance** | "对不对"：像不像、接不接得上、好不好看 | **人看片** | **人** | **不能** |

**C 路日常说的"结构通过 / 技术通过 / 审美通过"就是上表的三行**（structure / technical media /
creative acceptance）。**三者必须分别留证，不得互相冒充。**

> 本库门禁的四类输出（structure / reference / media / cost）是**执行门禁的分类**，
> 不是验收层级 —— 对照关系：`structure`+`reference` → 验收的 structure 层；
> `media` → technical media 层；`cost` 属预算闸（不属验收层级）。

### 1.1 平台自己写明的边界（照抄，不许当耳旁风）

- `export_readiness.evidenceBoundary`：**"Sources are readable; rendering and playback are not verified."**
  → **预检通过 ≠ 渲染正确**；
- `get_agent_status`：**"Reading data back is not playback or visual acceptance."**
  → **读回数据 ≠ 验收**；
- `check_continuity.limitations`：**角色外观、服装、空间轴线、光照、动作接续和色彩连续性
  必须查看实际像素/视频后判定**；
- `show_generation_result` 工具自述：**"A card does not certify generation completion or
  visual/audio quality."** → **结果卡片不是验收证据**。

**这四条合起来是一句话**：平台把"机器能判的"和"只能看片的"分得很清 —— **门禁该学这个姿态**。

### 1.2 三条不许说的话（没有判据支撑时）

```text
不许说"看着像" / "感觉对了"
不许说"门禁过了所以能交付"          （门禁只判结构，不判画面）
不许把"预检通过"说成"渲染正确"      （平台原文：rendering and playback are not verified）
```

**门禁的非 0 结果必须分类**（§7）。**"没验到"（rc=3）永远不等于"通过"。**

## 2 · 回读通道（**读边、读全文、读状态各有一条最省的**）

| 要什么 | 用哪个 | 成本 | 关键点 |
|---|---|---|---|
| 边数变没变 | `read_project(view="summary")` 的 `counts.edges` | 0 | **最便宜的哨兵**，比拉全量省两个数量级 |
| **真实边清单** | **`project_info` 的 `connectionList`** | 0 | 每条含 `source`/`target`/`sourceHandle`/`targetHandle`/`type`；**这是引用一致性的直接证据** |
| 节点全文 / `data` | `project_info` 的 `nodeList`（含 `data`，`desc` 是 prompt 纯文本副本） | 0 | ⚠ 输出极大（8 节点 ≈ 9 万字符）→ **只在要读边或读全文时用** |
| 单节点权威参数 | `read_node` | 0 | 同时给 `params`（当前存的）与 **`taskInfo.taskParams`（这一次真正提交的）** |
| 版本化快照 | `get_project_snapshot(section=…)` + `expectedRevision` | 0 | revision 绑定："changed projects are rejected instead of mixing versions" |
| 验收 | `inspect_media` / `export_readiness` | 0 | `inspect_media` 是**有界审查证据**，不做 ASR、不重生成 |
| ~~结果卡片~~ | `show_generation_result` | 0 | **不是证据**（§1.1 原文） |

### 2.1 ⭐⭐ `taskParams` 才是"这次到底吃了什么"（【已验证】）

`read_node` 会同时给出两份：`params`（节点当前存着的参数）与 `taskInfo.taskParams`
（**这一次生成真正提交进去的东西**）。

**【已验证】反例（2026-10-03）**：改完提示词再点火，回读得 `params.prompt`＝新版、
`taskParams.prompt`＝**旧版**，`taskParams.duration` 也是旧值 —— **那次生成完全没吃到修改，
等于白花一笔积分**。

**→ 纪律：改参数 → 点火 → 回读 `taskParams`。三者缺一，就等于没验证。
只读 `params` 是最常见的假验证。**

### 2.2 ⚠ 读通道本身可能是坏的（先自检，别急着怀疑画布）

读回恒 0 / 工具不在索引时，按三层判（授权 → 批准 → 挂载）自上而下定位；
**判"挂载"只看两处**：工具索引有无对应工具 + 连接器状态有无该条目。
**诊断顺序：先查配置注册，再查凭据，再查网络。**

## 3 · 结构回读判据（可机判）

### 3.1 引用闭合：三件套逐节点核

```text
① 被引用节点出现在引用字段里（left / leftAdd；首帧还要进首帧槽位）
② 它在 prompt 里以 {{node_key}} 插桩
③ 它已生效（有产物、url 非空）
```

**三件套缺一 → 结构不通过。** ⚠ 平台**不会**因为漏插桩而拒绝生成：
实测有 `status:2` 成功但提示词完全没插桩该主角的节点 → **必须回读提示词逐条核对，不能只看状态**。

### 3.2 位次：必须逐位看 key，不能只看长度

`imageListOrder` 的**长度**只反映条数；**顺序对不对必须逐位看 key**。
判据：`left`（请求的边）与 `imageListOrder`（重算结果）应一致，且与预期顺序一致。
**位次＝建节点时 `left` 数组顺序，事后不可重排**（见 §20 §2.1）。

### 3.3 三类硬缺陷（点火前必须清零）

| 缺陷 | 判据 | 工具 |
|---|---|---|
| **悬空端点** | 边两端 id 必须都在节点集合里 | `graph_plan_lint` / 边表对账 |
| **重复边** | 同一 (source,target,kind) 出现 >1 次（会放大权重或引发校验异常） | 同上 |
| **废弃/失败引用** | 废弃集合 与 实际引用集合 做差集，命中即阻断点火 | 台账 × 边表对账 |

### 3.4 ⚠ "某节点无入边" ≠ "链路断了"（本库踩过的过度断言 → 已查明）

`connectionList` **只记录部分关系**：合成节点的 `clips` 源、时间线承载的片段、
数据层字段（`data.*`）都可能**不在边表里**。

**【已验证 · 2026-10-07 查明】** 本地快照里 W2 的 33 个「智能剪辑」节点有 **12 个在边表里无入边**，
当时记的是【不可判定】。用逐节点转储复核后结论是：

```text
① 装配关系在 `data.clipTimelineData.clips` 层，不在边表：33/33 份 clipsAuthoritative = true；
② 而且那些 clips 的源 nodeId **全部不在 project_full_w2 的节点表里**
   → 因为节点表本身会静默漏节点（W2《重大发现_节点表会静默漏节点》，2026-10-05：
     `counts.nodes = 762` 是"平台记账数"，不是"可枚举数"）。
→ 所以"无入边"与"悬空边"都是**漏读造成的假象**，不是装配链断。
```

**→ 沉淀成一条通用纪律**：

```text
边表看到的"缺口"，先问一句"是不是我读得不全"，再问"是不是真的断了"。
判据：同一份数据里若存在 (a) clips/时间线层承载、(b) 节点表漏读 这两种可能，
      就**不许**写成"链路断"——要么补读全量，要么明确标注证据边界。
```

## 4 · 媒体门禁（技术通过）

### 4.1 判据链

```text
① 节点状态 = 已生效，且有真实产物 URL（url 非空）
② 导出前预检：export_readiness 的四个数组全空
③ 容器参数复核：ffmpeg -i（时长/分辨率/fps/有无音轨）
④ 抽样看片（这一步属于人的审美验收，不属机器门禁）
```

### 4.2 ⭐ `export_readiness` 的四个"不能导出"原因数组（【已验证】）

`ready:false` 时**先看这四个哪个非空**：

| 数组 | 含义 |
|---|---|
| `missingNodes` | 节点不存在 |
| `unavailableMediaNodes` | 节点在但**媒体没落盘**（"全建不点火"必中此条） |
| `invalidMediaTypeNodes` | 类型不对 |
| `invalidNodeKeys` | key 非法 |

`executionContract.unsupported` 实测原文含：
`speed` · `transitions` · `transforms` · `subtitles` · `per_clip_volume` · `per_track_volume` · `audio_source_trim`

**→ 在时间线上设了转场 / 变速 / 变换 / 字幕，导出时会静默丢弃。**
**交付纪律：转场与变速回本地剪辑软件做；字幕不要在平台内加。**

### 4.3 两条容器级陷阱

- **导出会强制生成一条音轨** —— 源视频都没声音，成片里仍出现 `aac 48kHz stereo 2kb/s`（≈静音）
  → **"零音轨"只能要求到源素材层**；
- **导出必然重编码**（无 `bitrate`/`crf`/`fps` 字段）→ **降低损失的规避手段**：
  `resolution`/`aspect_ratio` 留空跟随源、源片段尽量同规格、
  **不要把已合成的成片再当源反复多级合成**（同片迭代用 `edit_video_v4` 的 `clip_node_key`）。

### 4.4 ⚠ 合成前的混音电平陷阱（**能成功导出、但成片不可用**）

合成**不会自动平衡电平**：视频原声与叠加音轨线性相加，再由峰值限幅器整体拉低。
**只要保留视频原声，叠加的配乐/旁白就会被压到几乎听不见** —— 而且**不会被任何 readiness 拦截**，
往往到最后看成片才发现。
**→ 统一环境声时必须设 `video_volume = 0`。**

## 5 · 平台事实漂移（模型 · URL · hash · 快照）

### 5.1 模型漂移

- **平台没有 changelog 接口** → 只能靠**三源快照 diff**被动发现：
  `doctor`（`toolRegistry.revision` + `count`）· `get_capabilities`（契约版本）·
  `search_models`（逐条 `modelKey` + `labels` + `requiresWhitelistPermission` + `vip`）；
- **四类告警都要报**：新增 / 消失 / **改默认** / 改权限 ——
  尤其**改默认**（如 `enableSound` 默认一变，我方"假设静音"的流程会静默出错）；
- **我方纪律：逐镜显式写 `enableSound`，永不依赖默认**；
- `labels` 是**运营标记不是权限**；`requiresWhitelistPermission: true` ＝ 默认不可用需白名单
  （**以 `requiresWhitelistPermission` + 实际鉴权为准，不看 `labels` 猜**）。

### 5.2 URL 与媒体

- 产物 URL 在节点 `url` 字段（`https://libtv-res.liblib.art/...`）；
- **产物一旦生成，就与节点当前的 `params` 解耦** → **要用 `taskParams` / 实际产物反推成片，
  不能用 `params` 反推**；
- 画布是**活文档**：同一 id 的状态会随时间变化 → **跨任务读画布必须当场回读，不能引用旧观察**。

### 5.3 hash / `contentHash`：四条口径（【已验证】）

| 编号 | 规则 |
|---|---|
| `R-HASH-COV-1` | hash 覆盖率、唯一率、唯一内容占范围**必须分别报告**，并写明分母：`present/total`、`unique/present`、`unique/total` |
| `R-HASH-COMP-1` | 不同 revision / 范围 / 字段源 / 类型构成的 hash 数字**不得横向比较绝对数量**，也不得据此排名作品优劣 |
| `R-HASH-UNK-1` | **缺 `contentHash` 是【不可判定】**：不归入唯一、重复或缺媒体 |
| `R-HASH-DEL-1` | hash 相同**不能删除节点**；节点身份按 `nodeKey`，内容同一性才按 hash |

**三条不许混的**：

```text
不许把"缺 hash"写成"缺媒体"
不许把"来源路径与 hash 完全相关"写成平台按来源决定 hash（只能写相关性）
不许把本地 SHA-1/SHA-256 当平台 contentHash
```

### 5.4 快照与 revision

- `get_project_snapshot` 是 revision 绑定的：**changed projects are rejected instead of mixing versions**；
- 跨任务/跨作品比较**必须先锁 revision 并列出来**，否则数字不可比（`R-HASH-COMP-1`）。

## 6 · 失败分类（详见 21_ §5，这里只给归属表）

| 症状 | 责任层 | 回哪修 |
|---|---|---|
| 引用未生效 / 参考为空 | 引用层 | §3.1 三件套 |
| 位次错、主参考被覆盖 | 边/位次层 | §3.2 |
| 时长被截、枚举越界、字段被拒 | 平台适配层 | 21_ §1.2（以现场 schema 为准） |
| 参数改了没生效 | 平台适配层 | §2.1（读 `taskParams`） |
| 有产物但画面与 prompt 不符 | **安全降级** | 21_ §5.2 |
| 硬拒绝 / 部分审核拦截 | 审核层 | 21_ §5.1 |
| 时长/编码/像素问题 | 后期层 | 用 `ffmpeg` 判，不重生成 |

## 7 · 证据边界：只能记【不可判定】的清单

```text
快照只有 {id,name,type,position,width,height} 时：
  · video→video 边的合法性（缺 action，分不出 video_resource / video_generate）
  · 边参数一致（缺 params / modeType）
  · 段落是否按镜号分段（缺 prompt / 镜号）
  · 某剪辑节点无入边是"未接边"还是"由时间线/cips 承载"

平台侧：
  · 真实消耗（无余额/流水接口）
  · 平台按什么规则决定 contentHash（无 schema / 任务日志时的根因）
  · 导演台 capture/record 的计费与是否走同一审批
  · 1.5 五功能在 MCP 的隐藏暴露面
```

**记【不可判定】不是失败，是把"没验到"和"通过了"分开。**

## 9 · 验收清单

```text
结构层
☐ 边表已回读（connectionList），不是靠 imageListOrder 间接推断
☐ 引用三件套逐节点核过（left + {{key}} + 已生效）
☐ 位次逐位核过（不只看长度）
☐ 悬空 / 重复 / 废弃引用 = 0
☐ 无入边的节点已按【不可判定】处理，没有写成"链路断"

技术层
☐ 每个被引用的节点 url 非空
☐ 合成/导出前 export_readiness 的四个原因数组全空
☐ ffmpeg -i 复核了容器参数（时长/分辨率/fps/音轨）
☐ 导出不会用到的字段没有写在时间线上（转场/变速/字幕）
☐ 混音前已确认 video_volume 设置（避免叠轨被压没）

证据层
☐ 每一笔生成：任务号 + taskParams 快照 + 结果路径 + 判据原始输出
☐ 非 0 门禁结果已分类（既有债务 / 本批回归 / 未验到 / 不适用）
☐ 审美验收明确标注"待人看片"，没有用结构门禁冒充

漂移层
☐ 引用模型清单时带了月份，并注明"非全量"
☐ hash 数字带完整分母与 revision
☐ 缺 hash 标【不可判定】，没写成缺媒体
```
