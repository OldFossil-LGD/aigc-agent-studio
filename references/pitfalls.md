# 操作错误清单（本库实操中真实踩过的 · 动手前必读）

> **何时读**：**每次开始一段新工作之前**，以及**改脚本 / 改文档 / 写记忆 / 跑长任务之前**。
> **为什么单独成文件**：`qa-failure-codes.md` 管的是**出片失败**（资产层/契约层/提示词层），`key-decisions.md` 第三节管的是**内容决策不改**。
> 两者都**不覆盖"流程与工具误用"**——这个缺口就是本文件。
> **★ 命名空间（2026-10-02 新增）**：本册的坑号是 **`PF##`**，不再用 `P##`。**原因**：库内 `camera-package-library.md` 的**器材包号**是 `P01–P17`，`package-extended.md` 的**补充包号**是 `P18–P34`；两者与本册原来的坑号 **同号**（`P10`–`P17` 与 `P18`–`P29` 完全重叠），**看不出所引的是哪个**。全库共 **152 处** `P##` 引用，其中绝大多数指器材包——**所以改的是本册，不是包号**。
> **★ 纪律：本清单只收"犯过的"，不收"可能犯的"。每条都附触发场景 + 正确做法，不写空泛的"要小心"。**

## 一、★★★ 反复出现的（出现 ≥2 次，必须默认防线）

### PF1 · 复制后忘删原件（**已犯 3 次**）

| | |
|---|---|
| **症状** | 用 Edit 把 A 内容搬到 B 处，新内容写进去了，**A 处的旧内容没删** → 同一段文字出现两次 |
| **代价** | 记忆文件字符数暴涨（曾 4857 → 5566，反向涨 709）；用户看到重复内容；**且很难自查出来** |
| **触发场景** | ① 压缩长文档（把某节内容挪到别处）② 重构章节编号 ③ 合并两个小节 |
| **★ 正确做法** | **改完立刻 `grep -c "<那段文字的关键词>"` 数一遍出现次数**——预期 1 次，得到 2 次就是没删干净 |
| **具体案例** | 2026-09-13 压缩 `MEMORY.md`：把「五之二」并入「五」时，new_string 里重抄了整段「五之二」内容，而原「五之二」还在下面 → **同一节出现 2 次**。`grep -n "^## "` 才发现。 |

### PF2 · Edit 时 old_string 含标题、new_string 忘带 → **标题被静默删除**（**已犯 2 次**）

| | |
|---|---|
| **症状** | 压缩/替换时 `old_string` 从标题行开始（或包含标题行），`new_string` 没把标题写回去 → **小节标题消失，正文并到上一节里** |
| **代价** | 文档结构损坏；**编辑工具不会报错**（它只做字符串替换），肉眼扫一遍也容易漏 |
| **触发场景** | ① 压缩时想"顺便去掉几个空行" ② 替换从标题开始的整块内容 |
| **★ 正确做法** | ① **`old_string` 尽量从正文开始，不要含标题行**；② 若必须含，`new_string` 必须原样带回；③ **改完 `grep -n "^## "` 打印全部节标题，数一遍** |
| **具体案例** | 2026-09-13 `MEMORY.md`：第一次删掉「## 二、两个把关脚本」；第二次又删掉「## 五、最值钱的方法论」。两次都是 `grep -n "^## "` 抓出来的。 |

### PF3 · 短 python 脚本忘 `import io` → **全部抓取结果在写盘时丢失**（**已犯 2 次**）

| | |
|---|---|
| **症状** | 脚本跑了很久（含网络抓取），最后 `json.dump` / `open(...,'w')` 时抛 `NameError: name 'io' is not defined` → **前面几十分钟的结果全没了** |
| **代价** | 6 分钟~几十分钟的抓取全部白跑；且因为是在**最后一步**才炸，日志上看起来"跑得很正常" |
| **根本原因** | 短脚本越容易漏 import（写的时候脑子里想的都是逻辑，import 位被跳过） |
| **★ 正确做法** | ① **脚本写完后先跑一个最小输入用例**（1 条数据），确认能完整走完"取→处理→写盘"再挂长任务；② **凡是长任务，先确认 import 段完整**（`io` / `re` / `json` / `subprocess`） |
| **具体案例** | `bili_creator.py` 漏 `import io` → **217 条已成功抓取的结果在最后写入时全丢**。补上后重跑才拿到 121 条。 |

## 二、★ 出现 1 次但代价大的

### PF4 · 用 bash heredoc / `python -c` 写含反引号的文本 → **反引号被当命令替换，内容被吞空**

| | |
|---|---|
| **症状** | 用 `python -c "..."` 或 `cat > f << EOF` 写含 `` `文件名` `` 的 Markdown → 所有反引号内的文字被 bash **当命令执行**，内容消失，输出一堆 `No such file or directory` |
| **代价** | 已写好的日志被写坏，只能**截断重写** |
| **★ 正确做法** | **凡是含反引号 / `$` / 引号的文本，一律用 Write / Edit 工具写，不走 bash**。这是硬规则，不是"尽量"。 |

### PF5 · 报"占比"这类结构数字不带样本取法 → **数字不可复现**

| | |
|---|---|
| **症状** | 写出"教学率 79.9%"这类精确数字，但没说样本怎么取的 → **换个词就变成 70.5%** |
| **代价** | 数字看着精确、实则近似编造；**别人无法验证、也无法复现** |
| **具体案例** | B站第一批（榜单+教程词）得 79.9%，第二批（纯创作者词）得 70.5%。同一指标差 9.4 个点，**差的全是采样方式**。 |
| **★ 正确做法** | 报占比**必须同时给三样**：① 样本怎么取的（查询词 / 来源）② 样本量 ③ 分类规则是谁定的。三者缺一，数字降级为"量级判断"并明确标注。 |

### PF6 · "已知结论不会变"是懒惰假设 → **该抓的没抓，结论就是错的**

| | |
|---|---|
| **症状** | 上一轮判定"重抓也是这个结果，不值得再跑" → **实际抓完结论变了** |
| **代价** | 带着错结论往下走；且这个错结论会写进总结、写进 skill |
| **具体案例** | 我曾判定"B站第二批重抓结论不会变（仍是教学主导）" → 真抓完发现**自述率从 1% 涨到 17%**，"1%"是榜单把好材料挤掉了。 |
| **★ 正确做法** | **先跑原始数据再下结论**。当"要不要再抓一次"的判断依赖"结论会不会变"时，**默认去抓**——抓的成本远低于错结论的成本。 |

### PF7 · 修"漏报"时顺手造出"误报"（→ 已升级为 E27）

| | |
|---|---|
| **症状** | 发现检查脚本漏报某词 → 直接把这个词加进禁用表 → **全库立刻冒出一堆误报** |
| **代价** | 误报会**训练用户忽略工具**（比漏报更隐蔽的危害）；且改回原状要重新验证 |
| **具体案例** | `ai_smell_check.py` 原表只收「呈现**出**」，漏了「呈现」。直接把裸词「呈现」加进表 → 立刻造出 3 处美术术语误报（立体主义"多视角同时呈现"、工程蓝图"以线框呈现"、细密画"以侧影呈现"）。 |
| **★ 正确做法** | ① **改判据前先拿真实语料量一遍**（全库扫描，看会命中什么）；② **补双向用例**——既要"该报的报了"，也要"不该报的没报"；③ 正解是只报**"报告腔句式"**（`DOC_TONE_PAT`），裸词放行。 |

### PF8 · `--flat-playlist` 让 title 为空 → **误判"返回 0 条"，白跑一轮**

| | |
|---|---|
| **症状** | yt-dlp 站内搜索加 `--flat-playlist` 后，title 字段为空被丢弃，看起来"一条都没搜到" → 误以为被限流，重试白跑 |
| **★ 正确做法** | **B站搜索禁用 `--flat-playlist`**；**判断"有没有搜到"要看原始 stdout 里有没有 `_type: url`**，不看 title。 |

### PF9 · 用 `nohup &` 直起后台脚本 → **被 shell 回收时杀掉**

| | |
|---|---|
| **症状** | 长任务用 `nohup ... &` 起，命令返回了，但进程随后被杀，结果没写完 |
| **★ 正确做法** | **一律用 `run_in_background` 参数**起长任务（这是本环境唯一可靠的方式）。 |

### PF10 · 脚本写到 `/tmp` → **Windows 下被转成 `C:\tmp`，找不到**

| | |
|---|---|
| **症状** | `cat > /tmp/x.py` 写入成功，`python /tmp/x.py` 报 `can't open file 'C:\tmp\x.py'` |
| **★ 正确做法** | **脚本写进工作目录**（用 Write 工具写绝对路径），不要用 `/tmp`。 |

### PF11 · 引用指标不看它测哪个维度 → **纪律写错方向**

| | |
|---|---|
| **症状** | 看到一个数字（如 0.343）就当成"某能力差"的证据，**没看清它测的是哪个维度** |
| **具体案例** | PersonaShot 的 **0.343 量的是「跨镜情绪轨迹」，不是「单镜微表情」**——我一度混为一谈，差点得出"微表情是 AI 最弱项、必须绕开"的错纪律（实际单镜微表情已大幅改善，《鲸鱼之歌》靠它拿百花奖最佳技术）。**【待确认项】** 本条把 0.343 记为「**跨镜情绪轨迹**」，而 `key-decisions.md` C33 把同一个 0.343 记为「**单镜基准**」——**同一指标两种口径，未裁决**；**以 `key-decisions.md` 的登记为准，直到有人做一次受控实验**。 |
| **★ 正确做法** | **引用任何指标前，先回原始出处确认"它测的是 A 还是 B"**；把"跨镜"和"单镜"这类维度差当默认检查项。 |

## 三、纪律类（不是操作失误，但同样造成过返工）

### PF12 · 只改"来源节"不改"正文" → 等于没改

发现某个判据要变时，**只改了它诞生的那一节**，别处引用它的地方没同步。
**★ 正确做法**：**先 `grep` 出这个概念出现的所有位置，再逐个改**。改完再 `grep` 一遍确认全部更新。

### PF13 · 加了新模块没"接回主链路" → 写了等于没写

新写了一份文档 / 一个新章节，但**没有入口指针、没有样例、没有 eval 场景** → 用户默认路径永远走不到它。
**★ 正确做法**：新模块必须同时给三样——**① 在 `SKILL.md` 索引里有一行 ② 在 `start-here.md` 有入口 ③ 在 `evals/` 有对应场景**。
**★ 补充（2026-09-15）：顶格文件的入口只能"行内改写"。** 本库**有多份已接近或顶到 290／300 行**——
对顶格文件，**不要为了加一行去压缩别的段落**（那等于用"用户看得懂的话"换"一个内部文档的独立行"）；
正确姿势是**把新文件并进已有的那一行**（`start-here.md` §七 的做法），并且**优先把"用户会说的症状"补进那张给用户看的速查表**（入口要开在用户会看的地方，不是开在索引里）。
**★ 还有一处比索引更关键的入口：写提示词时真正会读的那一步。** 新层如果落在某个板块上，要**在模板文件的对应块附近留一行指针**（例：`character-realism.md` 挂在 `shot-craft.md` 的"第 7、9 块"那一行）——
**索引解决"找得到"，块附近的行内指针解决"在写的那一刻想得起来"。**

### PF14 · 凭记忆判断"这个概念库里有没有" → 一律不合格

**★ 正确做法**：加装任何东西之前，**逐字 grep 核对"这个概念的唯一定义在哪份文件哪一节"**（E20）。
- **答不出 → 真缺口，可以加。**
- **答得出 → 不是缺口，去补充现有那节，别新建。**
- **★ 进阶**：还要问"**覆盖到哪一层**"——找到概念 ≠ 它已覆盖到需要的那一层。（例：《时差》的"掉帧成母题"在库里能找到相近概念，但只覆盖到"身体部件层"，没覆盖"介质/信号层"。）

## 四、2026-10-01～02 LibTV 自动化轮（连续两日集中犯的 · 一律带触发场景）

> 这一段与上面三段不同：**上面是长期零散踩坑，这一段是同一天里连着踩的**——
> 说明它们不是"手生"，是**工作流里缺了一道默认防线**。每条后面都写了要补的那道防线。

### PF15 · 只读片段就动手改册（**已犯 2 次，两次都出整册级矛盾**）

**触发**：为了改某个判据，只读了目标册里"要改的那一段"，没通读全册。
**代价**：`asset-consistency.md` 的硬规格③（要 3/4 角度）与⑤（要中性正面）**整册自相矛盾**，
直到 `R3.6` 独立佐证才发现——**片段级阅读在原理上就发现不了跨节冲突**。
第二次：落 `R16` 才发现它与 `R9`／`R15` 打架。

**★ 默认防线**：**改册前整册通读（L1）**，或至少 grep 出被改概念在**全库**的出现位置。
"我看到的这一段没矛盾"**不是**结论。

### PF16 · 用 shell 改 CJK 文本（**已犯 3 次**）

**触发**：① PowerShell `-replace` 改中文；② `python -c` 内联 heredoc 写中文。
**代价**：「低饱和」→「腊近」；本轮又手滑打出 3 个 U+FFFD 替换字符。
**更隐蔽的一次**：PowerShell here-string 是**字面量**，`\n` 不会被转义成换行，
于是一行字符串被劈成两行 → `SyntaxError: unterminated string literal`，**报错信息离病因三行远**。

**★ 默认防线**：**改 CJK 文本只走「写 .py 文件 → 显式 UTF-8 → 跑」三步**，不走 `-c` 内联。
改完立刻 `U+FFFD` 全量扫一遍——**这是零成本的**，本轮就是靠它当场抓住的。

### PF17 · 把「平台侧 Agent 的自述」当结论

**触发**：平台 Agent 说"应该这样"，我直接写进册子。
**★ 口径**：**自述是线索，不是证据**。它给的**方向**可以采信并标注来源；
它给的**机制**必须等平台回读（`read_node` / `get_project_snapshot`）或 schema 实测来坐实。
**单次观察只能写"推断"**（L6）。

### PF18 · 不先探测工具可用性就开工

**触发**：整轮工作推进到"画布侧第 3 件待办"才发现 **LibTV MCP 早就掉线**。
**★ 默认防线**：**开工第一件事是探针**——`ListMcpResources(<server>)` 或一条最轻的读调用，
**通了再干活**。一个 5 秒的探针能省掉一整轮返工。
**判据**：**"我没收到报错"不等于"它通着"**——`unknown MCP server` 这类要主动去问才会出现。

### PF19 · 判据写成「有没有这个词」，而不是「逐项核」

**触发**：`R16` 写成 `("不采用" not in prompt or "用于" not in prompt)`。
**代价**：**一句糊弄全局也能过**——实测 spec 里两个节点屏上通过，实际一个"不采用"都没写。
**★ 默认防线**：写判据时问一句——**"如果我只写一句话骗过它，能过吗？"**
能过就是**判据太松**，不是内容合格。凡是"每个 X 都要 Y"，实现必须**按 X 循环**。

### PF20 · 把一个文件喂给多个「载体不同」的门禁

**触发**：`pipeline --shotlist` 把**同一份排镜表**依次喂给三个门禁。
**代价**：`sound_lint` 把「中景」当类别、把 `35mm 定焦` 当优先级 → **5 条假 FAIL**。
**为什么危险**：闸红了会被当噪声忽略，**真违规也就一起被忽略**（E23）。

**★ 默认防线**：接一个外部检查器之前先问——**它认的载体是什么**？
载体不同的检查器**必须分开入口**；没提供就记 `skipped` 并**点名说哪道没跑**，不许静默放过。

### PF21 · 判据完整性守卫漏覆盖新判据

**触发**：新增 `R12`–`R16`，喂了触发样例，**但没加进断言列表** → 守卫形同没有。
**★ 默认防线**：守卫的**列表和判据同步长**。加判据的那一步，**必须同时改守卫**；
`libtv_orchestrate.py` 的自检里有一条专测这条（"每条都能被触发"）。

### PF22 · 改自检数不同步回写库内数字断言

**触发**：自检 104 → 106，`SKILL.md` 还写 104。
**★ 好消息**：这次是 `audit_prompt claims` **主动抓到的**，不是我自己发现的——
**这正好证明"自检数必须有独立抽查机制"**。改脚本后跑一遍 `claims` 是固定动作。

### PF23 · 新册只被索引引用 → 孤立知识

**触发**：新建决策册，只在 `SKILL.md` 索引里提了一句。
**★ 默认防线**：新册落地后立刻跑 `lib_health`；被工作册引用才算有入口，
**只有记账册引用仍然算"学了没用上"**。

### PF24 · 新册的节标题与原册逐字相同 → 跨册重复长句

**触发**：两个册都用同一句 `## 一、Established（有实测支撑，改需数据）`。
**★ 默认防线**：新册的节标题**必须带本册限定词**，别照抄原册——否则 `lib_health` 判真重复。

### PF25 · 说明文字里的中文数字被数字断言解析器当成实测值

**触发**：在 `SKILL.md` 写「**第一卷**已满 300 行…」→ `claims` 把它读成
「风格库分卷数 = 一」，与实测 13 不符 → **假 FAIL**。
**★ 默认防线**：库内正文里**避免"第X册/卷 + 数量"的相邻写法**；
改完 `claims` 必跑。看不懂的报错先怀疑**自己新写的句子**，再怀疑判据。

### PF26 · 落新内容前不看行数余量

**触发**：`key-decisions.md` 到 289/300 才想对策。
**★ 默认防线**：**要往册子里写东西之前先看它还剩几行**；余量 ≤10 就**先拆卷**，
或者**另开一册**（并在原册留指针，否则触发 PF23）。

### PF27 · 把「CLI 传参错误」当成「检查通过」

**触发**：`lib_health.py .` 无输出、`rc=0` → 我以为没问题；
其实该脚本**不接受位置参数**，正确用法是不带参数。
**★ 默认防线**：`rc=0` **不等于**扫到了东西——**先看输出里有没有结论行**，

### PF29 · **被截断的表格行在 Markdown 里不报错**

**触发**：写长行内容时（特别是 heredoc / 临时脚本），行末的 `|` 丢了、或行内的剩余内容整段丢失。
**代价**（2026-10-02 扫出 **7 处**）：包括 `key-decisions.md` 四行 E 条目的**尾部整段丢失**（文本停在半句、证据列与日期列不存）。**为什么一直在漏**：
- ① Markdown 把行尾缺 `|` 的行当**普通文本**，**不会报错**；② `lib_doctor`、`claims`、`index`、`U+FFFD` 扫描**全部拿不到**（它们核的是「文件在不在」，不是「内容完整不完整」）；③ 读起来像「就是写断了」，**很容易被当成原本就这么短**。

**★ 已做到的**：`lib_health.py` 新增第五类检查「**表格行完整性**」——以 `|` 开头的行必须以 `|` 结尾（跳过分隔行与代码块），不符即 rc=1。已做正反两向证伪：真截断行 → rc=1；完整行 → rc=0。**★ 2026-10-02 修正本条的一句话**：我原写「这类错字**只能靠回读、无法自动化」——**过于绝对**。实测：参考语料只有 **3485 个不同汉字**，手写码位写错那一类**大多落到生僻字上**（本轮实测抓到「中途绒的诊断」「也吓掉了」「不计费」）。已落 `lib_health.py` 第六类检查「库内从未出现的汉字」（**只报不判 FAIL**，因为合法新术语也会引入新字）。**真正自动化的是「手写码位」那一类，而不是「常用错字」**；**常用错字仍只能靠回读**。**结论不反**（还是要回读），但**“一点都自动化不了”是错的**——应说「**自动化能拿多少**」。 每当你发现「某个门禁一直拦不住某类错」，先问「**它核的是什么维度**」——很多次的答案是「盘点不足」，而不是「判据写错了」。
