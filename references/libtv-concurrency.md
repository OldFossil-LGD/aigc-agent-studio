## 一、契约可确证的三条（按「已定」用）

### ① 节点级互斥（★ 最重要的一条修正）

- **契约明文**：`run_node` **"Fails if the node is already generating"**。
- **→ 因此「一个画布同时只有一个活跃 run」的准确含义是 `single_writer`**：**同一资源（节点）同一时刻只允许一个写操作 / 一个活跃生成**，
  **而不是「全局只能存在一个 run 对象」**。
- **不要把它夸大成「全画布只能有一个 run 存在」**——**不同节点可被分别运行**。
- **「画布级是否全局只允许一个 run 持写权」契约未明文**；**「节点级互斥」才是明文**。

### ② `create_*_node` 只建不跑；只读随时可做

- **`create_*_node` 无 `run` 入参**——**点火由独立的 `run_node` 承担**，故**不存在 `run=false` 这个字段**（题目里的 `create_node(run=false)` 在本契约对应「调用 `create_*_node` 且不调用 `run_node`」）。
- **活跃 run 存在时**：**只读接口可调用**（读不持写权）；**建不点火的节点也允许**（它不触发生成、不与正在生成的节点抢同一节点写权）。

### ③ 并发上限 5 的作用域

- **规则**：**无依赖调用可并行，一次最多 5 个**。
- **作用域**：**run 级（更准确说是 agent 单步调度批）**——约束**同一时刻并行发起的工具调用数**；
  **它没有写明是账号级或项目级硬配额**，也**没有写明跨画布是否共享一个固定为 5 的账号池**。
- **工程建议**：跨画布并行时，**仍按「每轮每画布最多 5 个无依赖调用」自我节流最稳妥**。
- **★★ 2026-10-15 REA 补充（客户端侧口径 · `observed` · 静态字面）**：网页 chunk 原文「**免费任务已达并发上限（1 个）**，请等待当前任务完成后再生成。」→ **免费档的"任务并发"闸＝1**；会员权益侧文案为「{n} 个并发任务」「无限并发任务」。**它与本条 R26 的"一次最多 5 个无依赖调用"不是同一件事**——R26 说的是**工具调用批**，这条说的是**生成任务并发**。**两条并存，不得互推。** 证据：`libtv-platform-watch-rea-index.md`（整册）。

## 三、多画布并行

- **账号级上限**：**契约未规定**「同时打开画布数」上限，**也未规定后台并发 run 的账号总槽位**。
- **工程建议（经验，非平台承诺）**：**2–3 个活跃画布并行**（每画布每轮 ≤5 个无依赖调用），**把实际后端限流当作未知、用保守值规避**。

## 四、锁的获取与释放

**当前契约没有暴露显式的「画布写权锁」对象，也没有「查询当前持锁者」的专用接口。可观察的互斥粒度是节点生成态。**

| 环节 | 契约口径 |
|---|---|
| **获取** | 调用 `run_node` 且该节点当前未在生成时，**该节点进入 generating**（等同取得该节点的写 / 生成权） |
| **释放（成功）** | **生成完成（成功产出，节点变「已生效」）**时释放，使其可被再次 `run_node` |
| **释放（失败）** | 失败时释放（**节点应标废弃**） |
| **报错 / 超时 / 掉线** | **契约未规定自动释放时长与掉线回收策略**；`run_node` 在节点 generating 期间**重复调用会失败** |
| **查询"谁在跑"** | **没有专门锁查询接口**；可用 `get_node_details` / `search_canvas_nodes` **读节点状态间接判断**，但**契约未承诺返回一个 generating 布尔或持锁 run_id** |

## 五、★ 死锁 run 的解绑出口（按优先级 · 在没有 steer/stop 的现实下）

1. **只读核实状态**：用 `get_node_details` / `search_canvas_nodes` 确认节点**是否真的还在 generating，还是其实已完成 / 已失败**——**很多"卡死"是状态未知而非真死锁**。
2. **等待自然超时 / 回收**：**不重复点火**，给后端超时回收留出时间（**具体阈值契约未规定**），**轮询只读状态**。
3. **换节点续作（最稳的主动出口）**：对需要的产物**新建节点（标题加 v2/v3）**，在**新节点上 `run_node`**；**同一产物最多重建 3 次**。
4. **换画布隔离**：若怀疑是**单画布写路径阻塞**，把后续工作**放到新画布推进（不销毁旧画布）**。
5. **「新建 run 顶掉旧 run」**：**当前契约未暴露 run 顶掉机制，不能承诺其能安全解绑**；**除非平台明确提供该能力，否则不要依赖顶掉作为首选**。

## 六、run 顶掉时旧 run 未完成节点的处置

- **契约未暴露「run 顶掉」机制**，故**没有契约级答案**。
- **可确证的节点语义**：**节点是持久画布对象**——`create_*_node` 创建后即存在；**`run_node` 成功则产物落到同一 `node_key`（不新建节点）**；**失败则该节点无有效产物（应标废弃并新建）**。
- **推断（非承诺）**：更可能是**「保留节点壳、不自动重跑、需自行决定是否新建 / 重跑」**。
- **`auto_rerun` = false**：**契约中没有任何「顶掉后自动重跑」的机制；重跑必须由 `run_node` 显式发起。**

## 七、`ask_human` 与"永久卡住"

- **契约中真实的提问原语是 `ask_human`**：**它会暂停并等待用户作答**，**未设置「自动超时转永久」的时间**，**也未提供 API 侧强制解绑 / 跳过该问题的字段**。
- **唯一出口是用户对该问题作答**。
- **★ 工程建议**：**无人值守场景应避免发起非必要 `ask_human`，从源头规避永久等待。**
- **★ 调用规则**：**`ask_human` 必须单独调用（不能与其他工具同批并行）**，且会暂停等待。

## 八、长任务超时与「成片时长」的区分

**★ 契约未给出单次生成的超时秒数，也未给出 run 整体生命周期上限。**

**可观察的只有各视频模型的时长入参范围——这是「成片时长」，不是「执行超时」**（**别把两者混为一谈**）：

| 模型 | 成片时长范围 |
|---|---|
| **Seedance 2.5** | **4–30s** |
| **Wan 3.0 / Wan 3.0 Prime** | **2–30s** |
| Seedance 2.0 / 2.0 Fast | 4–15s |
| Kling O3 / Kling 3.0 / Minimax H3 | 5–15s |

**应对**：**超时只能通过只读轮询 + 失败后新建节点（v2/v3）来兜底，不能假设具体分钟数。**

## 九、断线接续

**当前契约是「节点持久化 + 产物落同一 `node_key`」模型**——**已被后端接受的生成任务挂在节点上，断线本身不等于取消**；**接续时应先只读再决定，而非盲目重发**。

**四步接续姿势**：
1. 重连后先用 `get_node_details` / `search_canvas_nodes` **读各节点是否已有产物（已生效）/ 无产物（未完成或失败）**；
2. **已有产物**：直接复用 `node_key`，**不重跑**；
3. **无产物且确认失败**：按规则**新建节点（v2/v3）再 `run_node`**，**不在原节点反复硬撞**；
4. **状态不明**：**先轮询只读，等待其落到确定态，再动作**。

**`submitted_task_lost_on_disconnect` = false**（已被接受的任务绑定在持久节点上，**通常不因断线丢弃**；但**契约未明文承诺送达 / 不重复**，故**以重连后读回的实际产物为准**）。

## 十、★「提问一批 + 读回另一批」最稳排布（可照做）

**关键约束**：`ask_human` **必须单独调用**（不能与其他工具同批并行）且会暂停等待；只读可在等待前后安全调用；**无依赖调用每批最多 5 个**。

| 步骤 | 动作 |
|---|---|
| **A（先读，不发问）** | 单独一批只读，对「另一批」目标用 `get_node_details` 批量读（**一次最多 5 个 node_key；多于 5 个分批**），**把状态取齐** |
| **B（再提问，独占一轮）** | **单独调用一次 `ask_human`**，把「一批」问题**尽量合并进这一次调用的 `questions` 数组**（单选 / 多选），**不要把 `ask_human` 与任何其他工具放同一批** |
| **C（等待期间不抢写）** | **用户作答前不发起 `run_node`**；如需补充读，**在不与 `ask_human` 同批的前提下**安排（最稳是发问前把需要的读都做完） |
| **D（拿到答复后）** | 按答复**批量 `create_*_node`（只建不跑），每批 ≤5**；再**按依赖分批 `run_node`，有依赖串行、无依赖并行 ≤5** |

**画布安排**：**提问涉及的节点**与**大批量读回的节点**若互不相关，**可分到两个画布**——**画布 1 专管「提问 → 待决策生成」，画布 2 专管「只读读回 / 盘点」**，避免单画布在等待提问时阻塞读回；**每画布每轮 ≤5**。

> **★ 与本库现行做法的一致性**：本库现用 **A/B/C 三画布池 + 提问与读回分任务**，**方向与它给的排布一致**；它额外确认了**"ask_human 独占一轮"**这条硬规则。

## ★★ 波次编排修正（**R23 · 2026-09-22**）

**★ 我方《钥匙》波次表的真实缺陷（被 R23 点名，已确认）**：
- **把同一对首尾帧镜拆到两批**（第 1 波放 S2、第 2 波放 S1）→ **核对首尾帧时容易错配**。**正解：首尾帧材料同批（S1/S2 一起）。**
- **第 1 波 6 镜超限**（无依赖并行 **≤5**）→ 应拆成 **第 1 波 S3/S5/S7/S8/S9（5 个）→ 第 2 波 S1/S2**。
- **两条不可越的先后**：**S6 不得早于 S4**（它依赖 S4 的锁接触关系）；**S10 不得早于 S9 落幅固化**（落幅**必须先抽成已生效的 image 节点**）。

**★ 排序判据（两级）**：
1. **基础判据（本库原有）**：**可运行 ＝ 已创建且其全部引用节点已生效** —— **编号只表达成片顺序，不表达可点火顺序**。
2. **升级判据（R23 · 与 `libtv-official-qa-part6.md` §20 同向）**：在基础判据之上做**拓扑排序** —— 按引用 / 首尾帧 / 续写依赖建 **DAG**，**每轮取入度为 0 的节点、按 ≤5 一批分组**；**加一条防环检查（续写链不能成环）**。

**★ 合成提交的粒度（R23）**：**一次提交全部镜头更稳** —— 顺序 / 转场 / 音画对齐由**一次合成**统一处理；**分次提交＝反复生成中间成片，既浪费又在接缝处产生二次压缩与对齐误差**。BGM / 旁白在**同一次合成的音频轨**里给起点，**不要事后叠**。

## ★★ 协作面：**节点级锁可以直接读**（REA 静态 · 2026-10-16 补）

> 出处：`outputs/libtv_rea_20261014/55_协作只读端点与去水印偏好.md`。**只读 GET；未调用、未写。**

三个**只读 GET**，都打 **`mediaApiOrigin`**、都用 **`token` 头**（不是 `Authorization`）、都带 `?projectId=`：

| 端点 | 返回 |
|---|---|
| `/api/v1/project/collaboration/session?projectId=` | 会话 |
| `/api/v1/project/collaboration/locks?projectId=` | **锁表**（见下） |
| `/api/v1/project/collaboration/members?projectId=` | 成员（把服务端 `data` **原样**给 `members`，**不逐行归一**） |

**`locks` 的形状（逐字）**：只收 **`nodeId` 非空字符串 · `userId` 非空字符串 · `lockedAt` 有限数字**
三样都合格的行，产出 `{ nodeId, userId, nickname（缺省 ""）, avatar（缺省 ""）, lockedAt }`。

**逐字错误分类**（三个函数同源）：`"invalid json"` · `"empty body"` · `"missing code"` ·
`"data not array"` · 非 0 码时 `d.message ?? "error"`。

**★ 对本册的意义**：§一「节点级互斥」与 §四「锁的获取与释放」此前**只能从错误码反推**；
**现在"哪个节点被谁锁着"可以直接读**（`nodeId` + `userId` + `lockedAt`，另带 `nickname` / `avatar` 供展示）。
**→ 排查"为什么写不进去"时：先读锁表，再看错误码。**

⚠ 这三个端点是**客户端实现证据**；**服务端契约（字段稳定性、权限要求）未验**。
