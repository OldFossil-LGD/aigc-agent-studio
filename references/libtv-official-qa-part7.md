## UV1 · 点火与提交接口说明

### UV1.0 先对齐命名（我侧底层 API ←→ 它侧工具）

| 我方底层 API | 它侧等价物 | 说明 |
|---|---|---|
| `create_node(..., run=false)` | `create_image_node` / `create_video_node` / `create_audio_node` | **特点一致**：只把全部生成参数"写"到节点上，节点处于【已创建·空结果】，**不扣费、不跑** |
| 点火已建节点 | **`run_node(node_key)`** | 把一个【已创建】节点推进为运行中→已生效 |
| 改已建节点参数（不跑） | `update_image_node` / `update_video_node` / `update_audio_node` | **只改你传入的，省略的保持现状；改完节点回到已创建态，需再 `run_node`** |
| `generation_submit(...)` | "创建即运行"的合并式入口 | 语义＝带着参数新建（并通常直接运行） |
| `read_node` | `get_node_details` | 读状态/产物/已存参数 |
| `left` 建边 → `imageList` | `reference_nodes` 引用字段 | **引用是根基，不要手填 `imageList`** |

**★ 关键心智模型**：节点有**三态**——**已创建**（参数在、无产物）/ **已生效**（运行完成有产物）/ **已废弃**（弃用或失败）。**"点火" = 把一个【已创建】节点推进为运行中→已生效。**

### UV1.1 把已建好（`run=false`）的节点点火：正确做法 & 与 `generation_submit` 的职责区分

- **正确做法**：对已存在节点调用"运行"动作——**`run_node(node_key)`**。**不要用 `generation_submit` 去跑一个已建节点。**
- **职责区分**：
  - **`run` / `update_node(run=true)`**：对象是【**已存在的节点**】，跑的是该节点身份（node_key/id）所指向的东西，**不负责新建**。
  - **`generation_submit`**：对象是【**一次生成提交**】，用 `request={model, params,...}` 描述"要生成什么"，语义上是"**带着参数新建**（并通常直接运行）"。**`source_node_keys` 只是告诉后端这次生成引用哪些既有节点，并不等于"运行那些节点"。**
- **一句话**：一个是"**跑这个节点**"，一个是"**按这份 request 提交一次生成**（通常落成新节点并跑）"。对 `run=false` 建出来的节点，走前者。

### UV1.2 `update_node` 带 `run=true` 时，跑的是已存参数还是本次参数？

- **纯运行动作**（它侧 `run_node` 只收 `node_key`）：**跑的是【节点当前已保存的全部参数】**，本次调用不传任何生成参数，**因此不存在覆盖**。
- **若 `update_node` 同时支持"改字段 + run=true"**：则是"**先更新、再运行**"，本次显式传入的字段会覆盖对应旧值，未传字段保持原值。
- **它给的建议**：**把"改参数"和"点火"拆成两步**——先 `update`（不跑）确认参数，再 `run`（只传 id）。这样点火是幂等的"运行当前节点"，**不会误伤参数**。

### UV1.3 `generation_submit` 的 `request.source_node_keys` 格式，及与 `left` 建边是否等价

- **格式**：按字段名 `source_node_keys`（复数）与 `reference_nodes` 的契约，它是【**字符串数组**】，即 `["node_a","node_b"]`；**不是逗号拼接的字符串，也不是"JSON 数组再字符串化"**。提交时以原生数组放进 request 里序列化。
- **与 `left` 建边的关系**：
  - **信息层面相近**：二者都让系统把这些节点纳入本次生成的输入，并参与 `imageList/imageListOrder` 之类的重算。
  - **但不等价**：`left` 是【**在画布上建图结构的边**】，会**持久改变节点连接关系与重算结果**；`source_node_keys` 是【**本次提交请求体里的输入声明**】，**作用域是这一次 `generation_submit`**。用 `left` 建边后，边是节点状态的一部分；**只在 submit 里给 `source_node_keys`，不一定回写画布边**。
  - **★ 强约束（务必遵守）**：被引用的节点必须**同时满足**——**(a) 在引用字段里登记**；**(b) 在 prompt 文本里以占位符插桩**（它侧写法为**双花括号包裹节点 key**）。**只在文字里提到不算引用；只在 `source_node_keys` 里列而 prompt 不插桩，也可能导致模型拿不到该素材。**
  - `params.imageList` 由系统根据边/引用重算，**不可手填**。

### UV1.4 点火是否必须幂等键？同键同文重试安全吗？

- **`create_node` 上的 `idempotencyKey`**：用于"创建/创建即提交"去重，防止重复建节点或重复计费。
- **纯点火（`run_node` / `update_node(run=true)`）**：**没有独立幂等键字段**；幂等性建立在【**节点身份 + 当前状态**】上——对一个**已在运行或已生效**的节点再次发 run，**应被拒绝或直接返回当前状态**，而不是再起一条新生成（工具契约：**节点正在生成时 run 会失败**）。
- **安全重试建议**：
  - 网络不确定是否已触发时，**不要盲目再发 run**；先 `read`/`get_node_details` 看状态：已在跑则等待，已生效则取结果，**只有确认处于"可运行的已创建态"时才再发**。
  - 对 `generation_submit` 这类**会计费**的提交，重试要**复用同一个 `idempotency_key` 且保持 request 同文**，才是安全的"同键同文重试"；**换键或改文会被当成新提交**。
  - **同键同文通常安全**（后端去重为同一笔）；**同键不同文属于未定义/可能报错行为，不要依赖**。

### UV1.5 点火后怎么知道在跑/跑完：看哪个字段、轮询间隔

- 用 `get_node_details(node_keys)` 观察：
  - **是否已有输出/产物**——有产物即【已生效】。
  - **节点状态/生成状态字段**（`task_status`，以及节点三态）：典型取值区分 **排队/运行中**（`queued/running/pending`）、**成功**（`succeeded/completed`）、**失败**（`failed`）、**被拒/参数错误**（`rejected/invalid`）。
  - **已保存的生成输入**（`agent_task_params`：prompt、模型设置、引用节点）——用于核对"跑的是不是我想要的参数"。
- **判定优先级**：**先看是否"生成中"（running），再看终态**（成功有产物 / 失败 / 被拒）。
- **★ 轮询间隔建议（它给的）**：**图片类 2–3 秒一次**；**视频/音频类前 30 秒可 5 秒一次，之后 10–15 秒一次**；并做**最大等待上限与指数退避**，避免高频空转。**更优是有事件/回调就用回调，没有再轮询。**

### UV1.6 超时/失败时节点变成什么；如何区分"生成失败（可能计费）"与"参数被拒（未计费）"

| 类型 | 阶段 | 节点状态 | 计费 | 典型原因 |
|---|---|---|---|---|
| **参数被拒** `rejected/invalid/4xx` | **提交或点火的同步返回**就报错 | **停留在【已创建】**（参数还在、无产物） | **一般未进入生成、不计费** | 模型与类型不匹配、`duration` 超出该模型范围、分辨率非法、**引用了不存在或未生效的节点**、**prompt 缺少必需的节点 key 插桩占位符**、`imageList` 被手填 |
| **生成失败** `failed`（已进入执行） | 运行一段时间后 | **进入终态失败、无有效产物** | **取决于平台策略，可能已消耗额度** | 运行时错误、**内容审核**、上游模型超时、素材不可读 |
| **超时**（客户端等待超时） | —— | **不要直接当成失败** | —— | 先 `read` 节点——可能仍在跑，也可能已成功只是响应丢了。**以服务端节点状态为准** |

- **如何区分**：看 (a) **错误发生阶段**（同步校验即拒 vs 运行一段时间后 failed）；(b) **错误码/错误类型**（`invalid_argument/validation` 一般未计费；`execution/moderation/upstream` 一般已尝试执行）；(c) **是否有任务已启动/计费记录**。**无法确定时，凭任务 id/节点 id 查计费与状态，不要凭感觉重跑。**
- **它侧的失败处置纪律**：**不要在原节点反复重跑**；把失败节点**标记废弃**，**新建节点（标题加 v2/v3）**修正参数后再跑，并记录**旧 node_key 与失败原因**；**同一产物最多重建 3 次**。

### UV1.7 "先建后跑、批量点火"的推荐顺序与并发上限

**推荐顺序**：
1. **先批量 `create(run=false)`** 把所有节点参数落好（**不扣费**），人工/脚本核对 prompt、模型、引用、插桩占位符。
2. **用引用关系决定先后**：**可创建** = 已登记且其引用节点都已有 `node_key`；**可运行** = 已创建且其【**全部引用节点都已生效（有产物）**】。
3. **按依赖拓扑分批**：同一批内节点**互不引用、可并行**；被依赖的节点必须在**更早批次并已生效**，下游才允许点火。**不要把"引用了别人"和"被别人引用"的两个节点放进同一运行批。**
4. 每批点火后**轮询到终态**，成功再开下一批；失败先按 UV1.6 处置，**不盲目整批重发**。

**并发上限**：它侧对"无依赖的创建/调用"建议**一次最多 5 个并行**；**有依赖的串行**。批量点火也按**每批 ≤5 个、同批无引用关系**来控并发，避免触发限流。**被限流就退避重试，不要加键硬冲。**

### UV1.8 点火后发现参数写错，能停下来吗？

- **一般没有保证可用的"中途取消"**：一旦进入 running，多数生成模型调用**不可抢占**，通常要等它跑到终态。**在没有明确取消接口时，按"不可取消"设计。**
- **正确处置**：
  - 若刚提交、确认**还在排队（queued，未真正开始）**，可尝试取消接口（若有）；**没有就等终态**。
  - **不要在运行中对同一节点 `update` 参数**——运行中 update 会被拒，且即便改了也不会影响已经在跑的这一次。
  - **跑完后**：结果不要就当成品。**把该节点/产物标记废弃，修正参数后新建节点（v2）重新点火**；或用它侧 `update_*` 改参数（节点回到已创建）再 `run_node` 重生成。**注意：被引用节点一旦重新生成，引用它的所有下游节点现有结果应视为作废，需要按依赖链重新生成。**
  - **省钱做法**：坚持"**先建后跑、点火前核对**"，把参数错误拦截在 run 之前——**这也是 `run=false` 工作流的核心价值**。

## UV2 · 合成与导出（10 问）

> **★ 它的前置澄清（最重要）**：以下 10 问中提到的 `read_timeline`、`apply_timeline_edit`、`export_readiness`、`export_video`、`export_status`、`check_continuity` —— **在当前可调用工具集中并不存在**。当前环境真正承担"合成/导出"职责的接口是 **`composite_video`**；"连续性/调色"等能力由 **`edit_video_v4`**（专用剪辑 agent）承担；**时间线没有独立的读取接口**。

### UV2 · 名称映射速查（设想 → 当前真实接口）

| 设想接口 | 真实对应物 |
|---|---|
| `read_timeline` | **无可回读时间线**；时间线 = `composite_video` 的 `video_list/audio_list` 入参 |
| `apply_timeline_edit` | **`composite_video`**（拼接/混音）；复杂编辑 = `edit_video_v4` |
| `export_readiness` | **无独立预检**；调用时校验（节点有产物、key 类型、参数合法） |
| `export_video` / `export_status` | **`composite_video` 同步返回成片 VIDEO node_key**；`get_node_details` 看产物 |
| `check_continuity` | **无独立 checker**；`edit_video_v4` 分析 + `analyze_video` 人工核对 + 生成期锚点引用 |
| 调色 | **`edit_video_v4` 的 brief**（`composite_video` 不支持） |
| 音频对齐 | **`composite_video` 的 `audio_list[].start_time/end_time`** |

### UV2.1 `read_timeline` 返回什么？

- **没有 `read_timeline`，也没有独立的"时间线对象"可被读取。**
- **时间线是在调用 `composite_video` 时由入参即时描述的**，不落一个可回读的 timeline 实体。
- 最接近的真实结构就是 `composite_video` 的入参：
  - **`video_list`**：数组，**数组顺序即拼接（播放）顺序**；每个元素 `{node_key, start_position, end_position}`。
  - **`audio_list`**：数组，音轨**叠加**；每个元素 `{node_key, start_time, end_time}`，按 `start_time` 在成片时间轴上叠加（**混音，不是拼接**）。
  - **片段时长不是独立字段**，而是由 `end_position - start_position` 决定；**省略端点表示用整段**。
- **想"回看时间线"**：只能回看你自己保存的 `composite_video` 入参（建议把拼接方案写进工作文件，如 task-v2 的 storyboard ledger）。

### UV2.2 怎么把 10 个镜头按叙事顺序拼起来？

- **没有 `apply_timeline_edit`，用 `composite_video`。** 关键参数：
  - `video_list`：节点 key 列表（带可选裁切）；**顺序就是播放顺序**。
  - **每段时长**：通过每段的 `start_position` / `end_position`（秒）控制；**不填 = 该节点整片**。
  - `audio_list`、`audio_volume`、`video_volume`：叠加音频与音量。
  - `aspect_ratio`、`resolution`：画幅与分辨率（**不建议无脑指定**，见 UV2.6）。
  - `output_format`（**默认 mp4**）、`reuse_clip_node_key`（复用已有"智能剪辑"节点）。
- **注意**：`composite_video` 是"**拼接 + 混音**"，**不是逐镜时间线编辑器**；复杂剪辑（转场、字幕、调色、PiP）应走 `edit_video_v4`。

### UV2.3 "不能导出"的原因有哪些？怎么看返回？

- **没有独立的 `export_readiness`**；"是否可合成/导出"的校验**发生在调用时**，常见被拒原因：
  - `video_list` 里传的是**媒体 URL 而非画布 `node_key`**（必须先用节点承载素材）。
  - 引用的节点**尚未渲染完成 / 没有产物**（`edit_video_v4` 明确拒绝仍在生成的节点）。
  - `node_key` **不存在或类型错误**（如把非 video-clip 节点传给 `reuse_clip_node_key`）。
  - **裁切参数非法**（负数语义、`end≤start`、超出片段时长等）。
  - 音频/视频**节点类型与参数不匹配**。
- **怎么看返回**：**成功会返回新建成片的 VIDEO node_key；失败返回错误信息，按提示修正。** 合成前自行核对：10 个节点都已"已生效（有产物）"、key 真实、顺序正确、端点合法。

### UV2.4 `export_video` 的参数？成片放在哪里？

- **没有 `export_video`；导出成片即 `composite_video` 的返回值。** 相关参数：
  - `resolution`：**480p / 720p / 1080p / 1440p / 2160p**（**短边口径**；此为合成 / 导出档——视频生成节点档为 480p / 720p / 1080p / 4k，2160p≈4k 同物）；省略 = 跟随源。
  - `aspect_ratio`：**16:9 / 9:16 / 1:1 / 4:3 / 3:4 / 2:3 / 4:5 / 5:4 / 21:9**；省略 = 跟随源。
  - `output_format`：**mp4（默认）/ mov / mp3 / wav**。
  - **质量**：**没有单独 `quality` 档位字段**；清晰度由 `resolution` 体现。
  - **"输出节点名"**：**没有自定义输出名参数**；产物以**新 VIDEO 节点**落画布，可用 `reuse_clip_node_key` 复用已有"智能剪辑"节点避免堆积。
- **成片位置**：作为一个**新的画布 VIDEO 节点**（node_key 由接口返回），**不是本地文件路径**。需要入库可再用 `save_asset`。

### UV2.5 `export_status` 状态枚举？一般多久出片？

- **没有 `export_status`，也没有可轮询的导出任务号/枚举。** `composite_video` 作为工具调用**同步返回结果 node_key**（合成在后端完成后返回）。
- **因此没有官方 `queued/rendering/succeeded/failed` 枚举可查**；节点层面可通过 `get_node_details` 看节点是否已有产物。**耗时取决于 10 段总时长、是否重编码、分辨率与队列，无固定 SLA。**

### UV2.6 导出会重编码吗？会二次压缩吗？怎么避免？

- **会发生重编码**：`composite_video` 要把多段拼接并混音，输出为统一容器（默认 mp4），这本身就是一次编码/混合；**当源之间编码参数不一致，或你指定 `resolution/aspect_ratio` 导致缩放时，必然重新编码，存在二次压缩与画质损失。**
- **降低损失**：
  - **省略 `resolution` 和 `aspect_ratio`，让输出跟随源**（避免缩放）。
  - 尽量保证 10 个镜头**同分辨率、同帧率、同像素宽高比、同编码参数**生成，减少拼接归一化转换。
  - **不做无谓的音量/格式转换**；容器保持源友好的 mp4。
  - **需要"零重编码无损拼接"时，当前接口不提供 stream-copy 直通**；外部可用 `ffmpeg concat demuxer + -c copy`（**仅同源同参可行**），**超出画布工具能力**。
- **★ 反向提醒**：**加入 `audio_list` 而不把 `video_volume` 设 0，会触发峰值限幅把整体混音拉低**，可能让原声/BGM 变小——这是混音层面变化，不是压缩，但要留意。

### UV2.7 `check_continuity` 的参数与返回？能查"人物不一致"吗？

- **没有名为 `check_continuity` 的独立接口。** 连续性/一致性核对主要靠两条路：
  1. **`edit_video_v4`**：专用剪辑 agent 会探查源、拉逐字稿、检视帧并规划时间线；能在剪辑上下文中发现明显不连贯，**但不能重绘**（不能换脸/换背景/风格迁移）。**它是"带剪辑目的的分析"，不是返回结构化连续性报告的纯校验 API。**
  2. **生成期一致性**：靠锚点（角色/场景图）+ 引用关系（`reference_nodes` 与 prompt 内占位符插桩）保证，**而非事后 checker**。
- **"能否查出两镜人物不一致"**：**没有保证检出的自动比对接口**。可用 `analyze_video`（逐段视觉分析）人工核对，或在 `edit_video_v4` 的 brief 中明确要求"检查并标注跨镜人物/服装/道具连续性问题"。**它可能指出问题，但不会自动修复像素级身份；身份一致性应在生成阶段用同一角色锚点 + 引用约束保证。**

### UV2.8 合成阶段能不能调色？

- **`composite_video` 不提供调色参数**（只做拼接/混音/画幅/分辨率/格式）。
- **要调色（colour grading），用 `edit_video_v4`**，在 **brief 里用自然语言描述**，例如："全片统一暖调、压暗高光、轻微青橙对比、饱和度 -10%，加 2.35:1 黑边"。它支持调色、转场、字幕、图形、PiP、音量曲线等。
- **`edit_video_v4` 没有固定"调色字段名"，意图写在 brief**；对歧义创意可能返回 `needs_confirmation`，确认后继续。**`create_image_node` 的 `cinematic_lighting_correction` 模板是给静帧用的，不是视频合成期调色接口。**

### UV2.9 音轨怎么对齐？`audio_list` 的 `start_time/end_time` 在哪个接口？

- **在 `composite_video` 的 `audio_list` 中**：
  - 每条 `{node_key, start_time, end_time}`：**`start_time` 是该音轨在成片时间轴上的起点（秒）**，`end_time` 是它在成片轴上停止位置；**省略 `end_time` 播放到自然结束**。
  - **多条音轨按各自 `start_time` 叠加混音（不是首尾相接）。**
  - **`audio_volume`**：`audio_list` 这些轨的整体线性音量（**0–1，默认 1**）。
  - **`video_volume`**：各视频自带声的音量（**0 = 静音**）。想要 BGM/旁白清晰、不要现场声，就 `video_volume=0`；否则原声与 `audio_list` 混在一起并触发限幅。 **★ 三轨电平（R27）：人声最高 · 环境音垫底 · BGM 最低，BGM/环境约低人声 18–25 dB（经验值，非平台规定，以试听为准）；多路线性相加后峰值限制会把整体压低，音轨开满反而使人声不清。** **★ 与 `enableSound` 的分工（R27）：`enableSound` 只管「随片声要不要」（对白/环境/音效由视频模型一并产出），它不会去调 TTS/音乐模型 —— 精修短片的标准做法是「分镜阶段 `enableSound=false` → 声音后置独立做（配音 TTS / 环境音效 / BGM 各自建音频节点）→ 合成时 `video_volume=0` 叠三轨」；★ 收益：改台词只重音频、不重视频。**
- **例（它原样给的）**：BGM 从头铺，旁白在第 12 秒进入 →
  `audio_list = [ {"node_key": "a-bgm", "start_time": 0}, {"node_key": "a-vo", "start_time": 12} ]`，`video_volume = 0`。

### UV2.10 只要"10 个单独视频文件 + 一份拼接说明"，不走合成行不行？

- **行，完全可以不调用 `composite_video`。** 做法：
  1. 10 个镜头各自是**独立 VIDEO 节点**（已生效即各自成片，可单独导出/使用）。需要入库用 `save_asset` 逐个保存。
  2. **"拼接说明"落成工作文件**（建议 task-v2：`write_file_v2` 写一份 storyboard/拼接 ledger），内容含：**播放顺序（镜头01→10）、每段 node_key、建议入点/出点（秒）、目标画幅/分辨率（建议"跟随源"）、音轨与 `start_time`、调色与转场备注**。
  3. 将来真要合成时，按这份说明直接填 `composite_video` 的 `video_list` / `audio_list`。
