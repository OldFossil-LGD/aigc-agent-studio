# LibTV 计费、积分与实测差异（R24 · 平台方答疑）

> **来源与证据强度（先读）**：本册全文来自**平台侧 Agent 投递到画布的 `Agent交付_R24积分与实测`**（节点 `i-x8mrmwxupj8m` · 画布 A `128b26b763444eafa5565aaab3d4ade4` · 读回 2026-09-22 09:56）。
> **★ 证据等级＝「平台方声明」，但**它自己两次写明"具体积分单价以账户内实际计费页/下单确认弹窗为准；不同模型版本与活动期可能调整"** → 因此本册所有**具体数值一律按 L6 记「拟订」，不记「已定」**；**结构性结论（哪些动作收费、失败退不退、预冻结机制）可当「已定」用，数值只当量级参考。**
> **★ 口径纪律（L4）**：本册数字**不进提示词、不进交付件**，只用于**排产与预算**；任何对外报价前回一手计费页核。

## 一、计费点清单：一次"生成"里哪些动作单独扣积分

| 动作 | 是否扣积分 | 时机 |
|---|---|---|
| **建节点**（`create_*_node`） | **不扣** | 只写参数，节点保持 empty |
| **点火 / 运行**（`run_node`） | **扣**（核心计费点） | **提交即冻结** |
| **重抽**（同节点再次 run） | **扣** | 每次都单独扣，按一次新生成计 |
| **转码**（格式 / 分辨率转换） | 多数**不单独扣** | 已含在生成计费中；若触发重渲染才计 |
| **合成**（`composite_video`） | **扣** | 属生成型服务，通常按**输出时长 / 规格**计 |
| **导出 / 下载成片** | **不扣** | — |
| **上传素材** | **不扣** | 占存储，不占生成积分 |
| **反推提示词**（图生文 / 分析类） | **扣** | 属模型推理，按调用次计 |

**一句话**：**只有"真正调用模型 / 渲染"的动作扣积分**——点火、重抽、合成、反推；建节点、上传、下载不扣。

---

## 二、图像单价的计费口径

- **口径**：按 **「分辨率档 × 张」**，不是单纯按张。
- **量级（拟订 · 以实际计费页为准）**：**1K ≈ 1–2 分 / 张 · 2K ≈ 2–4 分 / 张 · 4K ≈ 6–10 分 / 张**。
- **重抽规则**：**同一节点重抽 3 次 = 计 3 次**（每次 run 独立扣费，**不因同节点而合并**）。
- **默认**：分辨率未指定时走模型默认档（**多数为 2K 档**）。

---

## 三、视频单价的计费口径

- **口径**：以 **「秒」** 为核心计价单位，并叠加 **「分辨率档 / 模型档」系数**；对外常表现为"一条"的价格，但**该条价格 = 时长 × 档位单价**。
- **线性性**：同一模型、同一分辨率下**基本近似线性**——**8s ≈ 4s 的 2 倍**；但**部分模型存在档位起步价（最低计费秒数）**，故 4s→8s 可能**略低于**严格 2 倍，而 **4s 与 5s 可能同价**。
- **非线性来源**：换更高模型档（Pro / 4K）会**乘模型系数**，非线性。
- **默认**：时长取模型默认秒数（常见 5s），分辨率默认 720p。

## 四、分辨率 × 时长 → 积分量级表（单条 · 单次 · 拟订）

| 分辨率 | 时长 | 积分区间 |
|---|---|---|
| 480p | 4s | 约 8–15 |
| 480p | 8s | 约 16–28 |
| 720p | 4s | 约 12–25 |
| 720p | 8s | 约 24–45 |
| 720p | 10s | 约 30–55 |
| 1080p | 4s | 约 20–40 |
| 1080p | 8s | 约 40–75 |
| 1080p | 10s | 约 50–90 |
| 4K | 5s | 约 60–120 |
| 4K | 10s | 约 120–220 |

**默认行**：720p × 模型默认时长。

## 五、失败退分规则（四种情形）

| 情形 | 退不退 | 退多少 | 退到哪 |
|---|---|---|---|
| **生成失败**（系统 / 模型报错，非用户原因） | **退** | 全额退本次冻结积分 | **原路退回**（余额购的回余额；赠点 / 配额的回对应配额） |
| **审核拒绝**（内容合规拦截） | **一般退** | 多为全额（视为未产出） | 原账户；**屡次恶意提交可能受限** |
| **超时**（服务端超时未出片） | **退** | 全额 | 原账户 |
| **手动取消** | **看阶段** | **点火后、尚未实际开始渲染前**取消 → 通常全额解冻；**已进入渲染后**取消 → **可能不退或只退未消耗部分**（以弹窗提示为准） | 原账户 |

## 六、"生成成功但内容不满意"能否退分

- **不退**。技术上"成功出片"即完成服务，**单纯主观不满意不退分**。
- **无通用"首次不满意免费重抽"规则**；重抽即正常计费。
- **例外**：活动期 / 新用户 / 特定模型灰度可能给**有限次免费额度或补偿券**（属运营策略，非固定权益）；**确属明显质量事故**（花屏、黑屏、严重崩坏）**可走客服申诉，可能个案补偿**。

## 七、并发 5 的实际扣费顺序

- **冻结模式**：提交时按批 **「同时预冻结（授权占用）」5 条对应积分**，随后按实际开始渲染**逐条确认扣款**。
- **余额要求**：**账户余额需足以覆盖整批**，否则余额不足的条**会提交失败**。
- **部分失败**：某条失败 / 被拦截，**该条冻结额立即解冻释放回账户**，**不影响其余已在渲染的条**；成功条正常结算。
- **默认**：整批预检余额，**不足部分不点火**。

## 八、哪些接口不计费（免费区）

| 类别 | 是否计费 | 频控 |
|---|---|---|
| **预检类**（`validate_generation_plan` 等纯参数 / 配额预检） | **不计费** | **有调用频率限制**（按账户 / 分钟级 QPS 限流），超出返回限流错误**而非扣费** |
| **读类**（`read_project` / `read_node` / `task_status` / `read_timeline`） | **不计费** | **有速率限制**（QPS 或日调用上限）；建议轮询 `task_status` 时**用退避间隔** |
| **`run_agent`（`autoGenerate: false`）** | **结构性判断＝不计费**（**「已定」部分**：不产生任何生成任务） | **证据（实测 2026-09-22 11:22）**：投递节点 `i-yg3u7th8pcnb` 的 `taskInfo` 为 **`taskId: ""` · `status: 0` · `taskResult: ""`** → **从未提交任何模型渲染** → 按 §一「只有真正调用模型 / 渲染的动作扣积分」**不扣** |

**★★ 一条必须分清「已定 / 未证」的边界（2026-09-22 补）**
- **「已定」**：**`autoGenerate: false` 的 run 不产生生成任务 → 不触发计费点**。这是**结构性结论**，有节点 `taskInfo` 为证。
- **「未证」**：**"与平台 Agent 对话本身是否计费"——平台无任何明文**（`get_capabilities` / 工具自述 / 本册来源 R24 答疑**均未提及** `run_agent` 或"对话"的计费口径）。**★ 注意：我方两个自动化提示词里那句"与平台 Agent 对话不计费"是此前按经验写下的假设，不是平台口径 —— 现已改为标注「未证」。**
- **「无法自证」**：**`account_user` 不暴露积分余额**（实测：只返回 `user` / `activeAccountId` / `accounts`（含 `memberAccount.accountLevel: 3`「标准版VIP 连续包月」）**，没有积分数值字段**）→ **我方目前无法用"余额前后对比"自行验证任何计费问题** → 要确认只能**看客户端计费页**或问平台。

## 九、同一 prompt 在不同模型上的实测差异（Wan 3.0 vs 其它）

| 维度 | Wan 3.0 | 其它（Seedance / Kling / Minimax H3） |
|---|---|---|
| **时长可控性** | **支持 2–30s、档位细、实际时长贴合度好** | 多为 **4–15s 固定档**，长片需拆镜或续写 |
| **角色一致性** | 多镜同角色脸部 / 服装保持**中上**，**依赖参考图** | **Kling 3.0 / Seedance 2.5 在强参考下更稳**；Minimax H3 偏动态、跨镜脸部偶有漂移 |
| **画面稳定性** | 运动连贯、伪影控制良好 | **高端档（Seedance 2.5 / Kling 3.0）高动态与光影更干净**；低价 / 快速档易出现轻微形变与闪烁 |
| **是否自行加字幕** | **默认不自行加字幕**（台词作为音频 / 口型，不烧字幕） | 多数同样不自动上字幕；**个别模型在识别到"标题感"文字 prompt 时可能把字渲染进画面** → **须明确写"无字幕 / 无文字"规避** |

**默认**：不自动烧录字幕（字幕统一在剪辑阶段加）。

## 十、非 VIP / 低价档模型的短板（点名退化项）

1. **首尾帧控制**：**常不支持或弱支持 end_frame（尾帧锁定）**——首帧支持但尾帧易丢，续写衔接不稳。
2. **参考图数量**：可挂参考图数量更少（多图 / 多角色参考受限），**多主体一致性下降**。
3. **时长档位**：上限更短（常见封顶 5–10s），无长片档，需更多拆分。
4. **分辨率**：默认 / 上限偏低，**4K 往往仅高档模型开放**。
5. **运动与物理**：复杂运镜、多人物交互、**手部 / 道具细节崩坏率更高**。
6. **音画**：对口型与环境音精细度下降。

**默认**：低价档默认 720p、短时长、少参考图。

## 十一、一次 34 秒 / 10 镜短片（含 3 锚点 + 若干重抽）的积分量级

**假设**：10 镜，平均约 3.4s/镜（按 4s 档计），主用 720p；3 个资产锚点为图像。

| 项 | 量级 |
|---|---|
| **3 张锚点**（2K 档） | 约 6–12 分（若含 4K 形象稿另加） |
| **10 镜首跑**（720p / 4s ≈ 12–25 分/镜） | 约 120–250 分 |
| **重抽缓冲**（按 30%–50% 镜需重抽 1 次） | 额外约 4–5 镜次 ≈ 50–125 分 |
| **合成**（约 34s 输出） | 约 30–80 分 |
| **合计** | **约 210–470 分**（按上列分项加总为 206–467，此处取整呈现）；若全程 1080p 或重抽更多，**上探约 500–700 分** |

**公式**：`总积分 = 锚点积分(张数×档位单价) + Σ(每镜秒数×分辨率单价×尝试次数) + 合成(输出时长×合成单价)`

## 十二、"先低价试跑再升档"流程与重复计费

- **是否官方推荐**：**是**——"低保真预检 → 低价 / 短时长 / 低分辨率试镜确认构图与动作 → 锁定后升档出正式片"。
- **步骤**：① 建节点不点火先批量审 prompt → ② 用快速 / 低价档 + 最短时长 + 720p 试跑关键镜 → ③ 确认分镜 / 首尾帧 / 参考图无误 → ④ 升模型档 / 分辨率 / 时长正式生成 → ⑤ 统一合成加字幕配乐。
- **★ 会重复计费**：**低价试跑是一次独立生成（扣费），升档重出是另一次生成（再次全额扣费）**。**试跑成本应视为「打样费」** → **只对拿不准的关键镜试跑**。

---

## 十三、把积分花在刀刃上（原话）

> **"先用建节点（免费）把分镜、参考图、首尾帧全部核对锁死，再用低价短档只给最没把握的镜头打样，确认后一次性升档出正片、把重抽压到最低——因为省积分的本质不是选便宜模型，而是减少『点火次数』。"**

## 十四、通用计费心智模型（一句话记牢）

**建节点 / 上传 / 下载 / 读取 / 预检 = 免费；一切「点火」（首跑、重抽、升档重出、合成、反推）= 按次 / 按秒 × 档计费；失败原路退，成功不退；并发按批冻结、失败条解冻。**

3. 片头三档（30/150/300）是**固定档位**而非按秒计价，与 Seedance 2.5 的「按秒计价」是**两种计价形态**，不可互相换算。
4. 本册原有的"生成前用 `power/calculator` 现算"仍是**唯一可执行口径**——客户端常数只用于**排产时的心算量级**。

## ★★ 官方「花钱与重试」边界（**LibTV 官方 `music-driven-product-ad/references/libtv-production.md` · 一手 · 2026-10-15**）

**① 付费范围**：付费只用于**计划内的那一次生成**，外加**单独授权**的参考图创建；**动手前**要确立用户授权**或**依赖对话里**已经明确**的授权。

**② ★★ 传输超时 ≠ 生成失败（本库此前零记录）**：官方原话 **"A transport timeout is not proof that generation failed."** ——**必须先回读"确切持久化的 node / task"再判断状态**；**任务完全可能在等待调用超时之后才完成**。

**③ 轮询没变化 ≠ 要重提**：**跟踪确切的 job / run ID 并监控它**；**不要因为某次轮询结果没变就重复提交**。

**④ 失败或有缺陷的结果不授权付费重试**：官方原话 **"A failed or defective result does not authorize a paid retry."** ——先**诊断提示词或参考**的问题，**再重新取得授权**，才能再跑一次完整生成。

**⑤ 积分不足**：**停下、保留会话与资产、报告确切状态**（不要"降级跑一个便宜的"）。

## ★★★ 报价响应形状 + 服务端「拦截结构」（**编辑器 bundle 静态 · 一手 · 2026-10-15**）

> 本节补上两个此前标"不可判定"的口子：**`power/calculator` 的响应体**，以及**服务端拦截时回传的结构化原因**。

### 一、`power/calculator` 的响应形状（**此前未观测，现已由消费端反推确定**）

官方的前端 hook 解析逻辑（逐字转写）：

```js
calculatePower(body).then(res => {
  if (res?.code === 0) {
    const power = res.data?.power;
    credits = typeof power === 'number' && isFinite(power) && power >= 0 ? power : '-';
  } else { credits = '-'; }
});
```

**→ 响应形状 ＝ `{ code: 0, data: { power: <number> } }`**；**非 0 或被拒时前端直接显示 `-`**（不抛错）。

**两条附带发现**：
1. **调用前有 300 ms 防抖**（`setTimeout(…, 300)`）——连续改动参数只报最后一次；
2. **★ 报价缓存键包含"权益状态"**：请求指纹 ＝ `JSON.stringify([rateLimitBenefitStatus, JSON.stringify(body)])` ⟹ **权益/限流状态一变，同一份参数的报价缓存即失效并重算**。
   **→ 纪律**：**不要把"上一次的报价"跨权益状态复用**；报价值只在"同一份 body ＋ 同一权益状态"下有效。

### 二、★★ 服务端拦截的**结构化字段**（此前只知道有拦截，不知道带什么）

前端有一个专门的解析器（`block_type` 若以 **`team_`** 开头则判为团队侧拦截并剥掉前缀）：

| 字段 | 含义 |
|---|---|
| **`block_type`** | **拦截类型**（可选前缀 `team_`；剥前缀后进"已知拦截码"白名单才认） |
| `model_name` | 涉及的模型 key |
| **`is_member_model`** | 是否会员专属模型 |
| **`estimated_cost`** | **预计消耗积分** |
| `group_id` | 分组 |
| `tool_call_id` / `toolCallId` | Agent 工具调用 id |
| **`billing_scope`** | 计费范围 |

## ★ 每动作积分拆解：`action_power_usage`（**编辑器 bundle 静态 · 2026-10-15/16**）

- 活动类型常量 **`action_power_usage`**（`role === "activity"`）；客户端解析出的形状是
  **`{actionId, llmPower, toolPower, totalPower}`**：`llmPower` / `toolPower` **各自缺省为 0**，
  **`totalPower` 服务端没给时用 `llmPower + toolPower` 自算**，`actionId` 是有限数字时**转成字符串**；
- **`totalPower <= 0`，或三个积分字段全缺 → 解析器返回 `null`、不渲染卡片**
  ⟹ **"界面上没有消耗卡" ≠ "这次没消耗"**——**要看字段，不要看 UI**；
- **意义**：这是**客户端可读的"单动作消耗、且把 LLM 与工具两段拆开"的通道**；
  **服务端怎么算出这两个数仍未验证**（本册只知其读取与兜底规则）。
